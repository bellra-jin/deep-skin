# Deep Skin — AI 피부 분석 · 맞춤 스킨케어 추천

## 데이터 전처리 · 부위별 등급 분류 모델 · AI 추론 연동

> 얼굴 이미지 한 장에서 부위별 피부 상태를 등급으로 정량화하고, 그 결과를 성분 추천까지 연결하는 서비스입니다.
> **"모델이 안 나오는 이유를 데이터에서 먼저 찾았다"** — 라벨 경계, 클래스 불균형, 크롭 비율을 차례로 좁혀 가며 ResNet-50의 한계를 진단하고 다음 백본으로 넘긴 기록입니다.
> 팀 프로젝트가 끝난 뒤에는 **AI-Hub 원본을 직접 받아 그 진단을 다시 검증했습니다** — 각도 필터의 오류를 찾아 학습 데이터를 48% 늘리고, GPU 없이 203개 조건을 비교해 백본 교체의 효과를 수치로 확인했으며, 부위를 눈가까지 확장해 그 결론이 어디까지 전이되는지 측정했습니다. 그 과정에서 라벨 문서의 오류 세 건을 찾았고, 시드 노이즈와 구분되지 않는 결론 하나는 철회했습니다(§6.5~6.10, §7.4~7.6).

## 3. 문제 정의

### 3.1 피부 등급 라벨은 경계가 모호하다

AI-Hub 라벨은 전문가가 매긴 0~5등급입니다. 문제는 **인접 등급의 경계가 사람이 봐도 모호하다**는 것입니다. 2등급과 3등급의 차이를 모델에게 구분하라고 요구하면, 실제로는 존재하지 않는 경계를 학습하게 됩니다.

여기에 **클래스 불균형**이 겹칩니다. 특정 등급에 데이터가 거의 없어서, 정확도만 보면 잘 맞히는 것처럼 보이지만 희소 등급은 아예 예측하지 못하는 모델이 나옵니다.

### 3.2 부위마다 크롭 크기와 비율이 다르다

같은 얼굴 이미지에서 잘라내도 부위별로 원본 픽셀 크기와 가로세로 비율이 크게 다릅니다.

- **미간** — 영역이 작아 확대하면 화질이 깨져 학습을 방해
- **이마** — 가로로 긴 영역이라 정사각형으로 resize하면 찌그러짐 발생

부위 특성을 무시하고 같은 전처리를 적용하면, 모델이 피부 상태가 아니라 **왜곡 패턴을 학습**하게 됩니다.

### 3.3 설계 원칙

- **모델을 바꾸기 전에 데이터를 의심한다** — 성능이 안 나오면 하이퍼파라미터부터 만지지 않고 라벨 정의·분포·전처리를 먼저 본다.
- **accuracy 하나로 판단하지 않는다** — 불균형 데이터에서는 macro-F1을 기준 지표로 둔다.
- **분류 라벨과 측정 수치를 섞지 않는다** — `annotations`(등급)와 `equipment`(장비 측정값)는 끝까지 다른 축으로 다룬다.
- **개선 시도는 실패해도 기록한다** — 되돌린 실험도 근거와 함께 남긴다.

`notebooks/jh/crop.py` · `docs/cheek/cheek_crop_pipeline_guide.md`

### 5.1 부위별 bbox 크롭과 각도 필터

AI-Hub 이미지는 7개 촬영 각도로 찍혀 있습니다. 문제는 **부위마다 가려지는 각도가 다르다**는 것입니다. 얼굴이 오른쪽으로 돌면 왼쪽 볼이 가려지고, 그 이미지를 학습에 넣으면 모델은 볼이 아닌 것을 볼이라고 배웁니다.

| 부위 | 사용 각도 | 제외 각도 | 기준 |
|---|---|---|---|
| 왼쪽 볼 | 정면 · 위 · 아래 · **R15° · R30°** · 왼볼 측면 | L15° · L30° | 얼굴이 오른쪽으로 돌아야 왼볼이 카메라 정면으로 온다 |
| 오른쪽 볼 | 정면 · 위 · 아래 · **L15° · L30°** · 오른볼 측면 | R15° · R30° | 얼굴이 왼쪽으로 돌아야 오른볼이 카메라 정면으로 온다 |

> 이 표는 **원본 라벨 10만 건의 bbox 통계로 검증해 한 번 뒤집힌 결과**입니다. 처음에는 각도 코드를 "어느 쪽이 보이는가"로 읽어 정반대로 필터링하고 있었습니다. 발견 경위와 수정 효과는 §6.6에 정리했습니다.

위·아래 각도는 제외하지 않았습니다. **조명과 각도 변화는 노이즈가 아니라 일반화에 필요한 다양성**이라고 봤기 때문입니다.

크롭 자체에도 세 가지 규칙을 넣었습니다.

```text
1. 파일명(_05, _06)을 믿지 않고 JSON 내부 images.facepart 값으로 부위를 확정
2. bbox에 각도별 margin(ANGLE_MARGIN)을 적용해 주변 맥락을 남긴 채 확장
3. 각도별 최소 해상도 규칙(ANGLE_QUALITY_RULES)으로 저품질 크롭을 걸러냄
```

margin을 각도별로 다르게 준 이유는 3.2에서 확인한 **부위·각도별 크롭 크기 편차** 때문입니다. 고정 비율로 자르면 어떤 각도에서는 경계가 잘리고, 어떤 각도에서는 배경이 과하게 들어옵니다.

### 5.2 ID 그룹 분할 — 데이터 누수 차단

`notebooks/jh/rebalance_split.py`

같은 사람의 사진이 train과 val에 동시에 들어가면 검증 점수가 부풀려집니다. 한 사람당 여러 각도·장비로 촬영된 데이터셋이라 **랜덤 분할은 곧 데이터 누수**입니다.

```text
1. train/val CSV를 합쳐 사람(id) 단위로 그룹화
2. 그룹별 라벨 분포를 집계
3. 희소 클래스를 먼저 덮도록 그룹을 선택하며 val 세트 구성
4. 사람 단위를 유지한 채 라벨 분포를 맞춘 CSV 재생성
```

무작위 분할이 아니라 **희소 클래스 커버리지를 우선하는 그리디 선택**입니다. 그냥 사람 단위로만 나누면 희소 등급이 한쪽에 몰려 검증이 불가능해지기 때문입니다.

### 5.3 라벨 체계 정리 — 분류와 회귀를 섞지 않는다

`docs/labeling_codes_guide.md` · `docs/cheek/cheek_training_prerequisites.md`

라벨 JSON에는 두 종류의 값이 같은 이름으로 들어 있습니다.

| JSON 영역 | 의미 | 학습 유형 | 예 |
|---|---|---|---|
| `annotations` | 전문가 진단 등급 | Classification | `l_cheek_pore` = 0~5 등급 |
| `equipment` | 장비 측정 수치 | Regression | `l_cheek_pore` = 측정값 |

**이름은 같은데 의미가 다릅니다.** 이걸 혼동한 채 학습을 돌리면 결과 전체가 무의미해지므로, 코드를 쓰기 전에 문서로 먼저 고정했습니다. 1차 학습은 `annotations`만 사용하고 `equipment`는 제외했습니다.

이 구분은 나중에 백엔드 DB 설계까지 그대로 이어집니다(§7.2).

## 6. 등급 분류 모델 학습

`notebooks/jh/train.py` · `model.py` · `configs/`

담당 부위는 **양쪽 볼(facepart 5·6)**, 예측 대상은 모공·색소침착 등급입니다. 아래 학습 코드와 설정은 볼 부위 파이프라인 기준입니다.

> **수치 출처** — 6.2~6.4의 성능 수치는 팀 발표 자료에 기록된 **3등급 전환 실험(검증 세트 기준)** 결과입니다. 부위별로 분해된 기록이 남아 있지 않아, 특정 부위의 성능으로 표기하지 않았습니다.

### 6.1 ResNet-50 학습 설계

```text
backbone    ResNet-50 (ImageNet 사전학습 가중치)
head        2048 → 512 (BatchNorm + ReLU + Dropout) → num_classes
optimizer   AdamW (weight_decay 1e-3)
scheduler   ReduceLROnPlateau
early stop  macro-F1 기준
```

백본은 `freeze` / `unfreeze`를 전환할 수 있게 분리했습니다. 데이터가 적을 때는 head만 학습시키고, 충분해지면 전체를 미세조정하는 두 전략을 같은 코드로 비교하기 위해서입니다.

실험 설정은 코드가 아니라 JSON으로 분리해, 조건만 바꿔 가며 재현할 수 있게 했습니다.

```jsonc
// configs/pore_run11.json
{ "target": "pore", "loss": "focal", "focal_gamma": 3.0, "oversample": true,
  "epochs": 80, "early_stopping_patience": 20, "batch_size": 8,
  "learning_rate": 1e-4, "weight_decay": 1e-3, "dropout_p": 0.3,
  "label_smoothing": 0.05 }
```

### 6.2 클래스 불균형 대응 — accuracy에 속지 않기

불균형 데이터에서 accuracy는 **다수 클래스만 맞혀도 높게 나옵니다.** 실제로 초기 실험에서 이 격차가 그대로 드러났습니다.

| 실험 조건 | Mean Macro F1 | Mean Accuracy |
|---|---:|---:|
| 3등급 · quick check | **0.303** | 0.673 |

정확도 0.673은 그럴듯해 보이지만 macro-F1 0.303은 **희소 등급을 거의 못 맞히고 있다**는 뜻입니다. 그래서 기준 지표를 macro-F1으로 고정하고, 불균형 대응을 두 겹으로 넣었습니다.

- **손실 함수** — `FocalLoss`(γ 조정)로 쉬운 다수 클래스의 기여도를 낮춤. 또는 label smoothing + class weight
- **샘플링** — `WeightedRandomSampler`로 배치 단위 클래스 균형
- **조기 종료** — accuracy가 아니라 macro-F1이 개선되지 않을 때 중단

### 6.3 5등급 → 3등급 전환 실험

모델이 아니라 **라벨 정의를 바꾸는 실험**을 했습니다. 0~5의 6개 등급을 **양호 / 보통 / 주의** 3등급으로 묶은 것입니다.

**근거**

- 인접 등급 간 경계가 모호해 모델이 존재하지 않는 차이를 학습해야 함
- 특정 등급의 데이터 부족으로 클래스 불균형이 심화됨
- 5등급 예측은 결과가 흔들려 신뢰도와 해석 용이성이 떨어짐
- 서비스에서 사용자에게 보여줄 단위도 결국 "양호/보통/주의"

**결과 (검증 세트 기준)**

| 실험 조건 | Mean Macro F1 | Mean Accuracy |
|---|---:|---:|
| 3등급 · ordinal optimized | **0.665** | **0.728** |
| 3등급 · balanced 보정 | 0.644 | 0.703 |
| 3등급 · quick check | 0.303 | 0.673 |

등급 병합으로 macro-F1이 0.303 → 0.665까지 올라갔습니다. **모델이 아니라 문제 정의를 바꿔서 얻은 개선**입니다.

반대로 **추가 균형 보정은 오히려 성능을 떨어뜨렸습니다**(0.665 → 0.644). 등급을 이미 3개로 합친 뒤에는 분포가 어느 정도 평탄해졌기 때문에, 그 위에 균형 보정을 또 얹으면 다수 클래스의 정상 신호까지 깎이는 것으로 보입니다. 이 실험은 되돌렸지만 **"해봤는데 안 됐다"는 근거와 함께 기록**했습니다.

### 6.4 한계 진단과 다음 백본으로의 전환

3등급 전환 이후에도 학습 곡선은 더 올라가지 않았습니다.

```text
3-grade ordinal ResNet-50 training curve (16 epochs, 검증 세트)

EPOCH 4 이후   val loss 정체 시작
EPOCH 11       best — macro-F1 0.665
EPOCH 11 이후  train / val macro-F1 간격이 계속 벌어짐 → 과적합
```

**학습 데이터는 잘 맞지만 새로운 데이터로의 일반화가 제한되는 패턴**입니다. 여기서 하이퍼파라미터를 더 만지는 대신 백본 자체의 한계로 판단했습니다.

| ResNet-50의 한계 | DINOv3 확장 필요성 |
|---|---|
| CNN 기반이라 미세한 피부 질감·색 변화 표현에 한계 (조명·그림자 영향) | 얼굴 여러 부위를 동일한 구조로 확장 가능 |
| Epoch 11 이후 검증 성능 개선 정체 | 소량·불균형 데이터에서 일반화 개선 가능성 |
| 부위별로 모델을 따로 학습해야 함 | 자기지도학습 — 라벨이 부족해도 학습 가능 |

이 진단을 근거로 팀은 백본을 **DINOv3 멀티태스크 구조로 전환**했고, 최종 서비스 추론은 그 모델이 담당합니다. 제 기여는 **전환 결정의 근거가 된 한계 진단과 실험 기록**까지입니다.

| | ResNet-50 | DINOv3 (팀 전환 결과) |
|---|---|---|
| 사전학습 데이터 | 140만 장 | 17억 장 |
| 학습 방식 | 지도학습 (라벨 필요) | 자기지도학습 |
| 백본 처리 | Fine-tuning | Frozen + Caching |
| 처리 부위 | 부위별 개별 모델 | 8개 부위 통합 |
| 작업 유형 | 분류 | 분류 + 개수 + 회귀 |

### 6.5 포크 이후 — 원본 데이터를 직접 받아 다시 검증했다

여기서부터는 팀 프로젝트가 끝난 뒤, 이 저장소를 포크해 **AI-Hub 원본(이미지 + 라벨 JSON, 22.6GB)을 직접 내려받아 볼 부위 파이프라인을 처음부터 다시 돌린 기록**입니다.

> **수치 출처 구분** — 6.2~6.4는 팀 발표 자료의 수치(백본 미세조정 기준)이고, **6.5부터는 제가 개인적으로 다시 돌린 실험 수치**입니다. 학습 방식(백본 동결 프로브)·분할(AI-Hub 원본 train/val)·전처리(각도 필터 수정 후)가 모두 달라 **두 수치를 직접 비교하면 안 됩니다.** 6.5 이후 수치끼리는 조건이 통제돼 있어 서로 비교 가능합니다.

목적은 세 가지였습니다.

```text
1. 전처리가 정말 의도대로 동작하는지 원본으로 확인
2. §6.4에서 "백본의 한계"라고 진단한 것이 사실인지 같은 조건에서 측정
3. GPU 없이(내장 그래픽) 실험을 반복할 수 있는 구조 만들기
```

작업 환경은 **CUDA 미지원 노트북(물리 4코어 CPU)** 입니다. 이 제약이 오히려 설계를 결정했고(§6.7), 그 설계가 다시 새로운 함정을 만들었습니다(§6.8의 시드 산포).

### 6.6 각도 필터가 뒤집혀 있었다 — 라벨 10만 건으로 확인

가장 먼저 한 것은 §5.1 각도 필터의 검증이었습니다. **크롭 결과를 눈으로 보기 전에는 필터가 맞는지 알 수 없다**고 판단해, 부위·각도 조합별로 크롭을 샘플링해 대조 시트를 만드는 스크립트(`angle_check.py`)를 먼저 짰습니다.

결과는 예상과 정반대였습니다.

**각도 코드는 "얼굴이 도는 방향" 기준이지, "어느 쪽이 보이는가" 기준이 아니었습니다.** 얼굴이 오른쪽으로 돌면(R15·R30) 카메라 정면으로 오는 것은 **왼쪽 볼**입니다. 원래 필터는 이걸 반대로 읽어, 가장 선명한 각도를 버리고 가장 납작한 각도를 학습에 넣고 있었습니다.

라벨 JSON 100,386건(train)의 bbox 통계로 확인했습니다. 아래는 **왼쪽 볼** 크롭의 가로/세로 비 중앙값입니다 — 값이 클수록 볼이 정면으로 와 넓게 잡혔다는 뜻입니다.

| 각도 | 의미 | 크롭 가로/세로 비 (중앙값) | 기존 필터 | 수정 후 |
|---|---|---:|---|---|
| 5 | R15° (얼굴이 오른쪽으로) | **1.16** | 제외 | **사용** |
| 6 | R30° (얼굴이 오른쪽으로) | **1.39** | 제외 | **사용** |
| 8 | 왼볼 측면 (패드·폰 전용) | **1.32** | 제외 | **사용** |
| 3 | L15° (얼굴이 왼쪽으로) | 0.52 | 사용 | 제외 |
| 4 | L30° (얼굴이 왼쪽으로) | 0.44 | 사용 | 제외 |

오른쪽 볼은 정확히 거울상이었습니다. 필터를 뒤집고, 품질 임계값도 감으로 정하지 않고 **15,444개 샘플의 백분위에서** 산출했습니다.

```python
# notebooks/jh/crop.py
# 각도 코드는 "얼굴이 도는 방향" 기준이다.
#   R15/R30 (5,6) -> 얼굴이 오른쪽으로 회전 -> 왼볼이 카메라 정면으로 온다
#   L15/L30 (3,4) -> 얼굴이 왼쪽으로 회전   -> 오른볼이 카메라 정면으로 온다
#   7/8 은 스마트패드·스마트폰 전용 측면.  7=오른볼용, 8=왼볼용.
ALLOWED_ANGLES = {
    5: {0, 1, 2, 5, 6, 8},  # 왼볼
    6: {0, 1, 2, 3, 4, 7},  # 오른볼
}
DEFAULT_QUALITY_RULE = {"min_width": 150, "min_ratio": 0.45, "min_area": 60000}
#   min_width 150  -> 상위 99.5% 유지 (0.48% 제거)
#   min_ratio 0.45 -> 상위 99.9% 유지 (0.06% 제거)
```

**수정 결과**

| | 수정 전 | 수정 후 |
|---|---:|---:|
| train 크롭 | 10,300여 장 | **15,295장 (+48%)** |
| val 크롭 | — | 1,908장 |
| 스마트폰·패드 비중 | 33% | **44%** |
| 크롭 오류 | — | **0건** |

데이터가 1.5배로 늘었을 뿐 아니라, **서비스 입력과 같은 기기(폰·패드)의 비중이 크게 올랐습니다.** 이 차이는 뒤의 도메인 갭 실험(§6.8)에서 그대로 의미를 갖습니다.

한 가지 덧붙이면, 대조 시트를 보고 처음에는 "크롭이 찌그러져 있으니 letterbox 패딩을 넣어야 한다"고 판단했습니다. 그런데 `dataset.py`를 다시 읽어 보니 **이미 `ResizeAndPad`가 train·val 양쪽 변환에 들어 있었습니다.** 찌그러져 보인 것은 제가 만든 뷰어가 정사각형으로 리사이즈했기 때문이었습니다. 멀쩡한 코드를 고칠 뻔했고, **문제를 발견했다고 생각했을 때 먼저 기존 코드를 다시 읽는** 순서를 배웠습니다.

### 6.7 GPU 없이 수십 개 실험을 돌리는 법 — 백본 동결 + 특징 캐싱

CPU만으로 ResNet-50을 전체 미세조정하면 **에폭당 1시간**을 넘습니다. 조건을 바꿔 가며 비교하는 것 자체가 불가능합니다.

그래서 **백본을 얼리고 특징을 한 번만 뽑아 캐싱**하는 구조로 바꿨습니다. 공교롭게도 이건 팀이 DINOv3로 전환하며 택한 `FROZEN + CACHING` 전략과 같은 발상입니다(§6.4 비교표).

```text
                 1회 (수십 분)                    반복 (수 초)
크롭 이미지 ──► [동결 백본] ──► .npz 특징 캐시 ──► [얕은 head 학습] ──► 지표
                                    │                  ▲
                                    └── 손실함수 · 등급 병합 · 샘플러 · 평가 프로토콜을
                                        바꿔 가며 재사용
```

전처리는 학습과 완전히 동일하게 맞췄고(`ResizeAndPad` → `ToTensor` → `Normalize`), 캐싱과 상충하는 증강 대신 **좌우반전 특징을 함께 저장해** head 학습 때 선택하도록 했습니다.

| | 소요 시간 |
|---|---:|
| ResNet-50 특징 추출 (train 15,295장 × 원본+반전) | 46.6분 |
| DINOv3 특징 추출 (train 15,295장) | 29.1분 |
| DINOv3 기기 열화본 특징 추출 (train 15,295장) | 22.1분 |
| **head 학습 1회 (60에폭, 조기 종료 포함)** | **5~22초** |
| **실험 203개 전체** | **약 90분** |

`train_head.py`는 다섯 축을 인자로 바꿔 가며 돌리고, 모든 결과를 `results/head_experiments.csv`에 한 줄씩 누적합니다.

```bash
uv run python notebooks/jh/train_head.py \
    --target {pore,pigmentation} \
    --grades {6,3} \
    --loss {ce,focal,coral} \
    --sampler {none,weighted} \
    --eval {standard,device}
```

### 6.8 실험 결과 — 무엇이 듣고 무엇이 안 들었나

실험 전체 기록은 `results/head_experiments.csv`에 있습니다(203건). 여기서는 볼 부위에서 결론이 나온 다섯 가지를 정리하고, 부위 확장(§6.9)과 방법론(§6.10)을 이어서 다룹니다.

> **수치를 읽는 기준 — 시드 산포**
> 아래 표는 별도 표기가 없으면 **단일 시드** 결과입니다. head 학습이 수 초로 끝나 조건을 많이 비교할 수 있었던 대신,
> 각 수치가 시드 운을 얼마나 타는지는 처음에 측정하지 않았습니다. 뒤늦게 (5)에서 같은 조건을 12회 반복해 재보니
> **전체 검증 macro-F1의 시드 표준편차는 0.0074**(범위 0.5632~0.5870), 표본이 410건뿐인
> **`--eval device`에서는 0.013~0.018**이었습니다.
>
> 그래서 이 문서에서는 **0.02 미만의 차이를 근거로 우열을 주장하지 않습니다.** 그 아래는 시드 노이즈와 구분되지 않습니다.
> 동일 시드 2회 실행은 완전히 같은 값을 내므로 재현성 문제가 아니라, 순수한 초기화·샘플링 민감도입니다.

**(1) 불균형 보정 3종은 전부 실패했다**

모공 등급은 6등급 중 등급 2가 **60.7%** 를 차지합니다. 데이터를 1.5배 늘린 뒤에도 이 비율이 그대로였다는 것은, **불균형이 필터 부작용이 아니라 라벨 자체의 성질**이라는 뜻입니다. 그래서 보정을 세 가지 방식으로 시도했습니다.

| 모공 6등급 · ResNet-50 | macro-F1 | 정확도 |
|---|---:|---:|
| 기준선 (CE) | 0.370 | 0.624 |
| Focal Loss | 0.373 | 0.630 |
| WeightedRandomSampler | 0.357 | 0.573 |
| 클래스 가중치 | 0.299 | 0.372 |

Focal은 사실상 무의미(+0.003)하고, 나머지 둘은 **오히려 떨어뜨립니다.** 팀 실험에서도 "3등급 전환 후 추가 균형 보정이 역효과"(§6.3)였는데, 6등급에서도 같은 결론이 나왔습니다. 손실 함수로 해결할 문제가 아니었다는 뜻입니다.

**(2) 문제를 고친 것은 등급 병합이었다**

| ResNet-50 | 6등급 | 3등급 | 변화 |
|---|---:|---:|---:|
| 색소침착 macro-F1 | 0.366 | **0.606** | +0.240 |
| 모공 macro-F1 | 0.370 | **0.545** | +0.175 |

여기서 한 가지 주의할 점을 기록해 둡니다. **검증 세트에 모공 등급 5가 0건**이라, 6등급 macro-F1은 항상 한 클래스가 0으로 잡혀 구조적으로 낮게 나옵니다. 존재하는 5개 클래스로만 평균 내면 0.370이 아니라 0.444입니다. 그래도 3등급 0.545에는 못 미치므로 **개선은 실재하지만, 표에 보이는 것만큼 크지는 않습니다.**

**(3) 백본을 바꾸면 오른다 — 그것도 같은 크기에서**

§6.4에서 "ResNet-50 자체의 한계"라고 진단했던 것을 같은 프로토콜로 검증했습니다. 비교 대상은 **DINOv3 ViT-S/16 (21.6M)** 입니다. ResNet-50이 25.6M이므로 **파라미터는 오히려 DINOv3가 적습니다** — "모델을 키워서 이겼다"가 아니라 **사전학습 방식의 차이만 남는 비교**가 되도록 고른 것입니다. 좌우반전 증강도 양쪽 모두 끈 동일 조건입니다.

| 과제 | 백본 | macro-F1 | 정확도 | QWK | 폰 F1 |
|---|---|---:|---:|---:|---:|
| 색소침착 3등급 | ResNet-50 | 0.606 | 0.644 | 0.685 | 0.578 |
| | **DINOv3 ViT-S/16** | **0.657** | **0.692** | **0.742** | **0.630** |
| 모공 3등급 | ResNet-50 | 0.545 | 0.650 | 0.402 | 0.479 |
| | DINOv3 | 0.563 | 0.654 | 0.436 | 0.499 |
| | DINOv3 + CORAL | 0.569 | 0.594 | **0.484** | 0.506 |
| 색소침착 6등급 | ResNet-50 | 0.366 | 0.457 | 0.640 | 0.273 |
| | DINOv3 | 0.400 | 0.528 | 0.728 | 0.339 |
| | **DINOv3 + CORAL** | **0.429** | 0.496 | **0.736** | 0.360 |

주목한 것은 **QWK(quadratic weighted kappa)** 입니다. 색소침착 6등급에서 macro-F1은 +0.03인데 QWK는 **0.640 → 0.736 (+0.096)** 입니다. QWK는 "몇 등급 차이로 틀렸는가"에 가중치를 주는 지표이므로, **DINOv3 특징은 맞고 틀림보다 등급의 순서를 훨씬 잘 담고 있다**는 뜻입니다. 피부 등급처럼 서수형 라벨에서는 이쪽이 실제로 중요한 지표입니다.

CORAL(서수 손실)의 거동도 이 해석을 뒷받침합니다. **ResNet-50 위에서 CORAL은 6등급 macro-F1을 0.378 → 0.356으로 떨어뜨렸지만, DINOv3 위에서는 0.400 → 0.429로 올립니다.** 부호가 반대라는 점이 핵심입니다 — 서수 손실은 특징이 이미 등급 순서를 담고 있을 때만 그 구조를 살릴 수 있습니다.

다만 **모공 3등급에서 CORAL이 CE보다 낫다고는 말할 수 없습니다.** 0.563 vs 0.569는 차이가 0.006으로, 위에 적은 시드 표준편차(0.0074)보다도 작습니다. macro-F1 기준으로는 두 조건이 구분되지 않고, 유의미하게 벌어지는 것은 **QWK(0.436 vs 0.484)** 뿐입니다. 색소침착 3등급의 백본 차이(+0.051)나 6등급 QWK 차이(+0.096)는 산포 대비 충분히 크지만, 모공 3등급의 백본 차이(+0.018)는 **경계선**입니다. 표에서 굵게 표시한 것은 이 기준을 통과한 값들뿐입니다.

**(4) 촬영 기기가 바뀌면 성능이 떨어진다 — 그리고 백본이 이걸 줄인다**

학습 데이터는 디지털카메라 비중이 높은데 **서비스 입력은 스마트폰**입니다. 이 도메인 갭을 직접 측정하려고, 디카(device 0)로만 학습하고 폰(device 2)으로만 검증하는 평가 모드를 넣었습니다.

| 디카 학습 → 폰 검증 (3등급) | ResNet-50 | DINOv3 | 변화 |
|---|---:|---:|---:|
| 모공 macro-F1 | 0.403 | **0.505** | **+25%** |
| 색소침착 macro-F1 | 0.523 | **0.568** | +9% |

같은 검증 세트 안에서 기기별로 나눠 봐도 방향은 같습니다(색소침착 3등급 기준 디카 0.596 → 폰 0.578 vs DINOv3 0.656 → 0.630). **자기지도 사전학습이 촬영 기기 차이에 덜 흔들린다**는 것이 수치로 나온 셈이고, 서비스가 폰으로 들어온다는 점에서 이것이 가장 실용적인 이득입니다.

**(5) 기기 열화 증강 — 평균보다 분산이 움직였다**

(4)의 격차를 더 줄이려고, 디카 이미지를 폰 촬영에 가깝게 열화시킨 특징을 학습에 섞었습니다.
특징이 이미 캐싱돼 있어 학습 루프에서 실시간 증강을 걸 수 없으므로, **열화본의 특징을 한 번 더 뽑아
사이드카(`_devaug.npz`)로 저장하고 좌우반전본과 같은 방식으로 확률적으로 교체**하는 구조를 썼습니다.

```text
디카 크롭 ──► 1/3 다운스케일 → 재확대   (폰의 낮은 실효 해상도)
          ──► 가우시안 블러 σ=0.9        (렌즈·후처리로 인한 미세 질감 손실)
          ──► JPEG 재압축 품질 40~60     (압축 아티팩트)
```

1차 파라미터(1/2 축소, 블러 0.6, 품질 55~75)는 효과가 없었습니다. 원인이 분명했습니다 —
크롭 원본이 약 600px인데 `ResizeAndPad`가 어차피 256px로 줄이므로 **1/2 다운스케일이 최종 리사이즈에
그대로 흡수**됩니다. 열화 전후 특징의 코사인 유사도가 0.995로, 사실상 같은 이미지였습니다.
강도를 올려 특징 변화폭을 9.6% → 14.9%로 키운 뒤에야 신호가 나왔습니다.

**결과 (5개 시드 짝지은 비교, `aug_prob` 0.5)**

| 조건 | 기준선 | 기기 열화 증강 | 차이 | 5시드 중 승 |
|---|---:|---:|---:|:--:|
| 모공, 디카 학습 → 폰 검증 | 0.518 (sd .013) | **0.531** (sd .006) | +0.014 | 4/5 |
| 색소침착, 디카 학습 → 폰 검증 | 0.573 (sd .018) | **0.595** (sd .006) | +0.022 | 4/5 |
| 모공, 전체 검증 | 0.579 (sd .003) | 0.582 (sd .002) | +0.003 | 5/5 |
| 모공, 전체 검증의 폰 subset | 0.467 (sd .015) | 0.480 (sd .010) | +0.012 | 4/5 |

**평균 상승폭보다 표준편차가 절반으로 준 것이 더 일관된 신호입니다.** 네 조건 모두에서 sd가 절반 수준이 됐고,
방향도 4~5승으로 일관됩니다. 열화 증강이 성능을 크게 끌어올렸다기보다 **학습을 안정화시켰다**고 읽는 편이
데이터에 맞습니다. 상승폭 자체(+0.014)는 시드 산포(0.013)와 같은 크기라, 단일 시드였다면 주장할 수 없는 값이었습니다.

한 가지는 검증되지 않았습니다. **기기 편차 자체가 줄어든 것은 아닙니다.** 전체 검증의 폰 subset은
0.467 → 0.480으로 올랐지만 디카·패드 대비 격차는 거의 그대로입니다. 실제로 줄어든 것은 기기 편차가 아니라
**시드 편차**이고, 두 가지를 섞어 말하지 않도록 여기에 구분해 적습니다.

**정리하면**, §6.4의 "백본의 한계"라는 진단은 **같은 조건에서 재현됐고**, 개선 방향도 세 가지로 구체화됐습니다 — 등급 병합(문제 정의), 백본 교체(표현력), 서수 손실(라벨 구조). 기기 도메인 갭은 증강으로 일부 완화됐지만 **여전히 가장 큰 남은 격차**입니다.

### 6.9 부위 확장 — 볼의 결론은 눈가로 전이되는가

볼에서 얻은 결론 세 가지(등급 병합, 백본 교체, 서수 손실)가 **부위가 바뀌어도 성립하는지**를 확인했습니다.
확장 대상은 **눈가(facepart 3·4)** 입니다. 볼과 좌우 구조가 같고 등급 범위도 같아서
파이프라인이 거의 그대로 붙기 때문입니다.

`crop.py`가 볼 전용으로 하드코딩(`FACEPART_DIR = {5: "l_cheek", 6: "r_cheek"}`)돼 있어
부위 정의를 테이블로 일반화하는 것부터 시작했습니다. 인자 없이 실행하면 기존과 동일하게 동작하도록
기본값을 유지했고, **볼 산출물을 재생성하지 않았습니다** — 볼 CSV의 컬럼명, 각도 매핑, 회귀 macro-F1(0.5820)이
모두 이전과 일치하는 것을 확인했습니다.

**문서 오류가 또 나왔습니다.** `l/r_perocular_wrinkle`은 문서상 0~5인데 **실제로는 0~6(7등급)** 입니다.
등급 6이 train 1,471건 / val 205건 존재합니다. 그대로 학습하면 인덱스 범위 초과로 죽습니다.

크롭 결과는 train 14,449 / val 1,810으로 볼(15,295 / 1,908)과 자릿수가 같습니다.
오류 32건은 전부 라벨 JSON의 bbox가 `null`인 데이터 결함입니다.

#### 전이된 것

| 볼에서의 결론 | 눈가에서 | 판정 |
|---|---|---|
| 등급 병합이 크게 이득 | 7등급 0.393±0.005 → 3등급 **0.624±0.003** | 전이됨 |
| 서수 손실(CORAL)이 QWK를 올린다 | 7등급 QWK 0.840±0.003 → **0.852±0.002** | **조건부** |
| 촬영 기기가 바뀌면 성능이 떨어진다 | 전체 0.624 → 디카 학습·폰 검증 **0.470±0.019** | 전이됨 |

**CORAL에 조건이 붙습니다.** 7등급에서는 QWK가 오르지만(+0.012, macro-F1은 0.393 → 0.391로 변화 없음),
**3등급에서는 QWK가 0.818 → 0.813으로 오히려 내려갑니다.** 등급이 3개로 줄면 임계값이 2개뿐이라
서수 구조에서 얻을 정보가 거의 남지 않습니다. §6.8에서 "특징이 등급 순서를 담고 있을 때만 CORAL이 듣는다"고
썼는데, **라벨 쪽에도 같은 조건이 붙는 셈**입니다 — 순서가 실제로 있어야 서수 손실이 작동합니다.

한 가지 더 눈에 띈 것은 **눈가 주름의 QWK가 유난히 높다**는 점입니다. 7등급에서 0.852인데
볼은 색소침착 6등급이 0.736, 모공 3등급이 0.484입니다. 같은 백본·같은 프로토콜인데
**라벨이 순서 구조를 담는 정도가 부위마다 크게 다릅니다.** 주름은 "깊어지는 정도"라는 연속적인 양이고,
모공은 개수와 크기가 섞인 복합 지표라는 차이로 보입니다.

#### 병합 경계를 지표로 고르면 안 됩니다

7등급을 3등급으로 묶을 때 경계가 자명하지 않아 두 가지를 모두 측정했습니다.

| 병합 규칙 | 클래스 분포 | macro-F1 |
|---|---|---:|
| **0-1 / 2 / 3-6** (볼과 같은 척도 위치) | 40.6 / 14.6 / 44.8 % | **0.624±0.003** |
| 0-1 / 2-3 / 4-6 (분포 균등) | 40.6 / 29.2 / 30.2 % | 0.749±0.004 |

숫자만 보면 후자가 0.125 높습니다. 그런데 **이 차이의 상당 부분은 macro-F1이 균형 잡힌 클래스를
유리하게 평가하는 성질에서 옵니다.** 라벨 정의를 바꿔서, 그 라벨 정의가 결정하는 지표를 최대화하는 것은
순환 논리입니다.

그래서 **척도 위치로 정했습니다.** 볼의 0~5 병합(0-1 / 2 / 3-5)은 척도의 2/6 · 1/6 · 3/6이고,
같은 비율을 0~6(7단계)에 옮기면 2/7 · 1/7 · 4/7 — 정확히 첫 번째 규칙입니다.
**더 낮은 0.624를 기본값으로 채택**했고, 0.749는 지표가 클래스 균형에 얼마나 민감한지 보여주는
감도 분석으로 남겼습니다.

#### 종횡비 가설은 기각됐습니다

§6.8-(4)에서 추론 엔진의 강제 정사각형 리사이즈가 성능을 깎는다는 것을 볼에서 확인했고,
**눈가는 bbox 종횡비가 0.38~0.43(볼 0.75)이라 왜곡이 2배 이상이므로 피해가 더 클 것**으로 예측했습니다.
이번 확장의 주된 목적이 그 예측의 검증이었습니다.

| ResizeAndPad → 강제 정사각형 | 볼 (ratio 0.75) | 눈가 (ratio 0.38~0.43) |
|---|---:|---:|
| 전체 검증 | **−0.0134** (0/5승) | +0.0045 (3/5승) |
| 폰 검증 | **−0.0317** (0/5승) | −0.0058 (3/5승) |

**예측과 반대입니다.** 눈가에서는 전체 검증이 오히려 미세하게 오르고, 폰 검증 하락폭은 볼의 1/5에 그치며
둘 다 시드 산포 안입니다. 볼에서 0/5승으로 명확했던 것이 눈가에서는 3/5승으로 **방향조차 일정하지 않습니다.**

왜 그런지는 측정하지 않았으므로 가설입니다 — 볼의 모공은 등방성 고주파 질감이라 가로로 늘리면
질감 통계가 깨지지만, 눈가 주름은 눈꼬리에서 뻗는 방향성 선형 구조라 가로 확대가 오히려
선을 두드러지게 했을 수 있습니다. 확인하려면 부위별 주파수 성분을 따로 봐야 합니다.

**실무적 결론**: 추론 전처리는 `ResizeAndPad`로 통일합니다. 강제 정사각형이 유의미하게 이기는 경우가
없기 때문입니다. 다만 **이득의 크기는 부위별로 다르며, "종횡비 왜곡이 성능을 깎는다"를 일반 명제로
쓰면 안 됩니다** — 볼에서는 깎고, 눈가에서는 차이가 없습니다.

#### 작은 크롭도 버리지 않는 편이 낫습니다

눈가는 볼보다 면적이 5.8배 작아, 볼 기준 품질 임계값(`min_width` 150)을 그대로 쓰면 데이터의 30% 이상이
버려집니다. 그래서 크롭 단계에서는 느슨한 하한(90)만 두고 **크롭 크기를 메타데이터에 기록해,
임계값 비교를 재크롭 없이 학습 시점에 하도록** 했습니다.

| train 하한 | n_train | macro-F1 | 차이 |
|---|---:|---:|---:|
| 90 (필터 없음) | 14,449 | **0.7490±0.0040** | — |
| 120 | 13,432 | 0.7469±0.0016 | −0.0021 |
| 150 | 12,419 | 0.7426±0.0025 | −0.0064 (0/5승) |
| 180 | 11,374 | 0.7415±0.0058 | −0.0075 |

단조 하락입니다. **작은 크롭을 버려서 얻는 것이 없습니다.**

이 표에는 함정이 하나 있었습니다. 처음에는 하한을 train과 val **양쪽에** 걸었는데,
그러면 임계값마다 검증 세트가 달라져(150에서 val 1,810 → 1,552) 성능 상승이 모델 개선인지
검증셋이 쉬워진 것인지 구분되지 않습니다. 실제로 그 측정에서는 150이 **+0.006으로 개선처럼** 보였습니다.
검증셋을 1,810으로 고정하고 train만 거른 뒤에야 방향이 드러났습니다.

### 6.10 측정하지 않은 것은 주장하지 않는다

실험을 43건에서 203건까지 늘리는 동안, **틀린 결론을 붙잡은 것보다 붙잡지 못할 뻔한 것들**이
더 많았습니다. 이 절은 그 방법론을 따로 정리한 것입니다.

#### 시드 산포 — 결론 하나를 철회했다

head 학습이 수 초로 끝나 조건을 수십 개 비교할 수 있었는데, **그 편리함 때문에 각 수치가
시드 운을 얼마나 타는지를 한참 동안 재지 않았습니다.** 같은 조건을 12회 돌려 보니 이랬습니다.

```text
전체 검증 macro-F1 (동일 조건 12회)
  평균 0.5724   표준편차 0.0074   범위 0.5632 ~ 0.5870
표본이 410건뿐인 --eval device
  표준편차 0.013 ~ 0.018
```

동일 시드 2회 실행은 완전히 같은 값을 내므로 재현성 문제가 아니라 **순수한 초기화·샘플링 민감도**입니다.
이 측정 이후 **0.02 미만의 차이로는 우열을 주장하지 않는다**는 기준을 세웠고,
그에 따라 §6.8의 "모공 3등급에서 CORAL이 CE보다 낫다"(차이 0.006)를 **철회**했습니다.

이후의 모든 비교는 5시드 짝지은 비교이며, 평균±표준편차와 승패를 함께 기록합니다.

#### 비교 조건을 고정하지 않으면 측정이 아니다

두 번 같은 함정에 빠질 뻔했습니다.

**하나** — 크롭 폭 임계값을 train/val 양쪽에 걸어 임계값마다 검증셋이 달라진 경우(§6.9).
150이 +0.006으로 개선처럼 보였지만, 검증셋을 고정하니 −0.006이었습니다.

**둘** — 기기 열화 증강 효과를 단일 시드 기준선(0.505)과 비교한 경우.
그 기준선은 시드 운이 나쁜 draw였고 5시드 평균은 0.518이었습니다.
정직한 수치는 **0.505 → 0.535(+0.030)가 아니라 0.518 → 0.531(+0.014)** 로, 절반입니다.

#### 교란 요인은 배제하고 넘어간다

"디카로 학습해 폰으로 검증"이라는 도메인 갭 실험에 **각도 교란**이 있다는 것을 뒤늦게 발견했습니다.
AI-Hub는 각도와 기기가 독립이 아닙니다.

```text
디지털카메라  각도 0~6      (7·8 없음)
스마트패드·폰  각도 0·7·8    (1~6 없음)
```

디카로만 학습하면 각도 7·8을 한 번도 못 보는데, 폰 검증 세트의 **51%가 그 각도**입니다.
그렇다면 "기기 갭"이라고 부른 것이 실은 미학습 각도의 효과일 수 있습니다.

검증 세트를 각도로 한 번 더 갈라 확인했습니다.

| 디카 학습 → 폰 검증 | n_val | 볼 macro-F1 | 눈가 macro-F1 |
|---|---:|---:|---:|
| 전체 | 410 / 388 | 0.5177±0.0148 | 0.4698±0.0194 |
| 각도 0만 (학습에서 본 각도) | 200 / 175 | 0.5268±0.0236 | 0.4692±0.0322 |
| 각도 7·8만 (학습에 없던 각도) | 210 / 213 | 0.5293±0.0078 | 0.4756±0.0105 |

**차이가 없습니다**(볼 +0.0026, 눈가 +0.0064, 둘 다 시드 산포 안).
미학습 각도라고 해서 더 나쁘지 않으므로, 도메인 갭은 **각도가 아니라 기기 자체**의 것입니다.
교란을 배제하고 나서야 "기기 도메인 갭"이라는 표현을 쓸 수 있게 됐습니다.

#### 문서를 믿지 않는다

작업 중 라벨 문서(`docs/labeling_codes_guide.md`)에서 오류 세 건을 찾아 정정했습니다.
셋 다 코드로는 드러나지 않고 **데이터를 세어야만** 보이는 것들이었습니다.

| 항목 | 문서 | 실제 | 확인 방법 |
|---|---|---|---|
| bbox 형식 | `[x, y, w, h]` | **`[x1, y1, x2, y2]`** | 문서대로 읽으면 표본의 71.2%가 이미지 경계를 벗어남 |
| 눈가 주름 등급 | 0~5 | **0~6 (7등급)** | 등급 6이 train 1,471 / val 205건 존재 |
| 패드·폰 각도 | 0~8 사용 | **0·7·8 세 개만** | 각도 1~6의 패드·폰 레코드 0건 |

좌/우 명명이 **관찰자(이미지) 기준**이라는 것도 함께 명시했습니다 —
`왼쪽 눈가`(facepart 3)는 이미지 왼쪽에 있고, 이는 **피사체의 오른쪽** 얼굴입니다.
읽는 사람이 해부학 기준으로 가정하기 쉬운 지점입니다.

#### 실험 기록

`results/head_experiments.csv`에 **203건**이 조건·지표·기기별 성능·소요 시간·**시드**와 함께 누적돼 있습니다.
시드를 기록 대상에 넣은 것은 위 산포 측정 이후입니다 — **시드를 적지 못하는 실험 로그는
자기 행을 재현하지 못합니다.**

과거 23건은 실행 명령을 확인할 수 없어 시드 칸을 **비워 두었습니다.** 기본값이었을 가능성이 높지만
추론이므로 채우지 않았습니다. 나머지는 실행 순서에서 복원한 뒤 **4개 행을 같은 시드로 재실행해
소수점 4자리까지 일치**하는 것을 확인했습니다.

## 7. AI 추론 연동

모델이 아무리 잘 나와도 **출력을 서비스가 받아 쓸 수 없으면 의미가 없습니다.** 학습과 서비스 사이를 잇는 구간을 맡았습니다.

### 7.1 추론 계약

`backend/docs/ai_inference_contract.md` · `backend/app/schemas/image_upload.py`

AI 추론 서버와 백엔드 사이의 응답 구조를 **스키마로 고정**했습니다. 모델이 바뀌어도 이 계약만 지키면 서비스 코드는 그대로입니다.

```text
POST {AI_INFERENCE_URL}   multipart/form-data
  file · session_id · user_id · image_id

응답 → InferenceResult 로 Pydantic 검증
  model_name · model_version · parts[]

parts[] 필수      raw_part_name · display_part_name · metric_name
                  issue_type · grade_value(int) · severity · confidence_score
parts[] 선택      predicted_value · measured_value      ← Optional, 하위 호환
```

`AI_INFERENCE_MODE` 하나로 추론 소스를 전환합니다.

| 모드 | 동작 |
|---|---|
| `mock` | 외부 호출 없이 고정 결과 반환 — 서버 없이 서비스 흐름 개발/테스트 |
| `remote` | 단일값 응답 서버 호출 후 스키마 검증 |
| `multivalue` | 부위 검출 + 멀티태스크 추론 서버 호출 — **현재 운영 모드** |

`scripts/dummy_ai_server.py`는 이 계약을 그대로 반환하는 검증용 목 서버입니다. 모델이 학습 중일 때도 서비스 계층을 계속 검증할 수 있었고, 실제 서버로 전환할 때 바뀐 것은 **URL과 파서뿐**이었습니다.

### 7.2 응답 파싱 — 등급 · 측정값 · 검출을 분리 저장

`backend/app/services/multivalue_parser.py`

추론 응답 한 건을 성격에 따라 네 테이블로 쪼갭니다. §5.3에서 정리한 **분류/회귀 구분이 그대로 DB 스키마가 된 것**입니다.

```text
AI 응답 1건
  ├─ annotations  → skin_part_results     등급값 (분류)
  ├─ equipment    → skin_metric_values    연속 측정값 (회귀)
  ├─ detections   → skin_part_detections  부위 bbox + bbox_source
  └─ 원본 JSON    → ai_raw_responses      전체 보존
```

같은 실수라도 출처가 다르면 다른 컬럼에 넣습니다.

| 컬럼 | 출처 | 저장 경로 |
|---|---|---|
| `grade_value` | 등급 판정 (0~3) | 공통 |
| `predicted_value` | 모델이 예측한 회귀값 | 이미지 업로드 추론 |
| `measured_value` | 장비·AI-Hub JSON 원본 측정값 | 개발용 JSON 입력 |

**부위 검출에 실패한 경우도 버리지 않고 기록합니다.** 검출된 부위는 `bbox_source = yolo`, 미검출로 전체 이미지를 사용한 부위는 `full_image_fallback`으로 구분 저장합니다. 값이 같아도 신뢰도가 다르기 때문에, "이 수치를 믿어도 되는가"를 나중에 판단할 근거를 남겨 둔 것입니다.

### 7.3 E2E 검증

`backend/docs/remote_ai_e2e_test_result.md`

업로드부터 리포트 렌더링까지 전 구간을 실제 이미지로 검증하고, DB에 무엇이 몇 건 들어갔는지 표로 남겼습니다.

```text
이미지 업로드 → 백엔드 이미지 검증 → AI 서버 추론 요청
  → 부위 검출 (미검출 부위는 전체 이미지 fallback)
  → 멀티태스크 추론
→ 응답 파싱 → 4개 테이블 저장 → 추천 생성 → 리포트 API → 화면 표시
```

검증 과정에서 **학습 라벨에 없어 항상 0으로 채워지던 지표(`chin_moisture`)를 발견해 응답과 저장 대상에서 제거**했습니다. 값이 있는 것처럼 보이지만 실제로는 추론되지 않은 값이라, 그대로 두면 사용자에게 거짓 정보를 주게 됩니다.

같은 이유로 등급 `0`이 **"미검출"인지 "이상 없음"인지**를 `bbox_source`와 함께 구분해 판정했습니다.

### 7.4 "한쪽 눈이 측정되지 않는다" — 검출기는 정상이었다

서비스에서 한쪽 눈가가 측정되지 않는 현상이 보고됐습니다. 원인을 세 가지로 좁혀 **라벨 108,070건을
전수 집계**해 확인했는데, **셋 다 거짓**이었습니다.

| 가설 | 검증 | 결과 |
|---|---|---|
| 좌/우 정의가 코드와 라벨에서 어긋난다 | 정면 이미지의 bbox 중심 x 비교 | **거짓** — 눈가·볼이 같은 규약(관찰자 기준) |
| 스마트폰 셀피 미러링으로 좌우가 뒤집힌다 | 기기별 중심 x 비교 | **거짓** — 디카 0.165 / 패드 0.233 / 폰 0.245, 전부 같은 쪽 |
| 눈가 각도 필터가 볼과 같은 오류를 갖는다 | 각도별 bbox 기하 통계 | **해당 없음** — 눈가 필터가 아직 존재하지 않았음 |

검출기 자체도 정상이었습니다. 저장소의 YOLO 학습 산출물(`images/yolo_confusion_matrix.png`)을 확인하니
**`l_eye` ↔ `r_eye` 오분류가 0건**이고, 전체 지표는 mAP50 0.994 / precision 0.994 / recall 0.991입니다.

```text
클래스별 재현율 (AI-Hub 검증셋)
  forehead 100%   l_eye 99.4%   l_cheek 99.5%   lips 100%
  glabella 99.8%  r_eye 98.6%   r_cheek 98.8%   chin 100%
```

**진짜 원인은 데이터셋 구조였습니다.** 정답 수를 보면 이마·입술·턱이 1,391건, 볼이 1,388건인데
**눈가만 1,124 / 1,144로 18% 적습니다.** 비정면 사진에서 가려진 쪽 눈가에는 **데이터셋이 애초에
라벨을 붙이지 않았고**, 검출기는 그대로 학습해 그대로 동작하고 있었습니다.
추론 샘플에서도 정면 사진은 양쪽, 강하게 돌아간 사진은 한쪽만 검출됩니다.

#### 그래서 문제는 검출이 아니라 그 다음이었다

```text
고개를 살짝 돌린 사진 업로드
  → 한쪽 눈가 미검출 (정상 동작)
  → bbox_source = full_image_fallback
  → 얼굴 전체 이미지로 "눈가 주름"을 추론
  → 다른 부위와 똑같은 모양으로 리포트에 실림
  → 사용자는 그것이 추정값인지 알 수 없음
```

**조용히 틀린 값을 내보내는 것이 검출 실패보다 나쁩니다.** 7.5와 7.6이 이 경로를 다룹니다.

한편 `detect_best_per_part()`가 **부위명당 최고 신뢰도 박스 하나만** 남기는 구조는 그대로 위험합니다 —
두 박스가 같은 좌우 클래스로 분류되면 반대쪽이 통째로 사라집니다. 관측된 적은 없지만
(혼동행렬 0건, 9개 각도 54장 추론에서 재할당 발생 0건) **도메인이 다른 실사용 입력에서는 보장되지 않으므로**,
좌우를 x좌표로 재할당하는 가드를 넣고 `lr_source`로 검출기 판단인지 후처리인지 구분했습니다.

### 7.5 등급 → severity 매핑 정본화

리포트에 표시되는 `severity`는 `normal / mild / moderate / severe` **4개 어휘로 고정**돼 있습니다.
소비처가 전부 `_SEVERITY_ORDER.get(severity, 0)` 패턴이라 **어휘 밖 값은 예외 없이 최저 등급으로
조용히 강등**됩니다. 여기에 두 가지 결함이 있었습니다.

| 증상 | 원인 |
|---|---|
| 등급 5가 `unknown`으로 누출 | `inference_engine.severity_map`이 0~4만 정의 |
| 등급 4가 정렬에서 최하위로 취급 | `"very_severe"`가 어휘 밖이라 `.get(x, 0)` → 0 |
| 눈가 주름 등급 6의 결과가 **통째로 사라짐** | 파서의 매핑이 0~5만 정의 → `None` 반환 → skip |

세 번째가 가장 나쁩니다 — **가장 심한 케이스가 리포트에서 없어집니다.**

정본은 `multivalue_parser._SEVERITY_BY_ANNOTATION`이고, 이미 **라벨별로 상한이 다른 것을 정규화**해
두었습니다. 미간(0~2)은 2가 `severe`, 이마 색소(0~3)는 3이 `severe`가 되는 식입니다.
여기에 7등급 전용 테이블을 추가하고, 추론 엔진의 평면 매핑을 정본에 맞췄습니다.

```python
_ZERO_12_345_6 = {0: "normal", 1: "mild", 2: "mild",
                  3: "moderate", 4: "moderate", 5: "moderate", 6: "severe"}
```

**어휘를 넓히지 않은 것이 핵심입니다.** `"extreme"`을 추가하는 편이 직관적으로 보였지만,
그러면 최고 등급이 정렬에서 최하위가 됩니다. 어휘가 4개로 고정된 계약이라는 것을 소비처를 전부 확인한
뒤에야 알았습니다.

### 7.6 추정값을 추정값이라고 표시하기

`bbox_source`(`yolo` / `full_image_fallback`)는 `skin_part_detections`에 **저장되고 있었지만
API 스키마에도 프론트엔드에도 없었습니다.** 저장만 하고 보여주지 않은 것입니다.
`(session_id, raw_part_name)`으로 조인되므로 마이그레이션 없이 노출할 수 있었습니다.

집계에 `mixed` 상태를 따로 두었습니다. 화면의 "눈가"는 `left_eye`와 `right_eye`를 묶는데
**측면 사진에서는 한쪽만 fallback**이 됩니다. 이진값으로 뭉개면 "양쪽 다 추정"과 "한쪽만 추정"이
구분되지 않으므로, 각각 "추정값" / "일부 추정"으로 표시합니다.

**값 자체는 숨기지 않았습니다.** 항목이 사라지면 사용자는 이유를 알 수 없습니다.
값은 보여주되 추정임을 밝히는 쪽이 맞습니다.

#### 정면 여부는 검출 결과만으로 판정할 수 있다

두 번째 방어선은 업로드 시점입니다. **추가 모델 없이** YOLO 검출 결과만으로 각도를 판정할 수 있고,
이 데이터셋은 모든 이미지에 정답 각도가 붙어 있으므로 **임계값을 감이 아니라 실측으로** 정할 수 있었습니다.
각도당 30장씩 270장으로 보정했습니다.

| 지표 | 정확도 | 오탐 | 미탐 |
|---|---:|---:|---:|
| 눈가 쌍이 모두 검출되는가 | 62.2% | 102 | 0 |
| **미간이 두 볼 중점에서 벗어난 정도** (임계값 0.05) | **94.8%** | **0** | 14 |
| 같은 지표, 임계값 0.06 | 95.6% | 5 | 7 |

첫 번째 지표가 실패한 이유가 중요합니다 — **L15·R15에서는 두 눈가가 모두 검출됩니다.**
한쪽이 사라지는 것은 L30·R30부터입니다. 샘플 몇 장만 보고 "측면이면 한쪽만 검출된다"고
일반화했다가 270장 실측에서 정정된 부분입니다.

임계값은 정확도가 더 높은 0.06 대신 **0.05를 택했습니다.** 오탐은 "측면 사진을 정면으로 통과시켜
추정값을 실측값처럼 내보내는" 실패이고, 미탐은 "재촬영을 한 번 더 권하는" 실패입니다.
**정확도는 같은 단위로 세지만 비용은 대칭이 아닙니다.**

남은 약점은 기록해 둡니다 — 위를 본 사진(angle 1)은 96.7%로 잘 잡히지만 **아래를 본 사진(angle 2)은
66.7%** 입니다. 고개를 숙이면 미간이 볼 중점에서 밀리는 것으로 보이며, y축 항을 추가하는 보완이 필요합니다.

## 8. Backend · Frontend 연동

### Backend (FastAPI, `:8000`)

- 인증(JWT) · 프로필 · 분석 세션 · 이미지 업로드 · 추론 호출 · 추천 · 리포트
- 이미지 검증 파이프라인 — 확장자 / MIME / 크기 / Pillow 유효성 확인 후 저장
- 실패 시 `uploaded_images.failure_reason`과 `analysis_sessions.error_message`에 사유를 남겨 **어디서 끊겼는지 DB만 봐도 알 수 있게** 처리
- MySQL + SQLAlchemy + Alembic (마이그레이션 `0001` ~ `0008`)
- 추천은 `(부위, 이슈, severity)` 규칙 매칭 후 프로필의 민감성·알러지 성분으로 필터링

| 메서드 | 경로 | 설명 |
|---|---|---|
| `POST` | `/analysis/sessions/{id}/images` | 업로드 → 검증 → 추론 → 결과·추천 저장 |
| `GET` | `/analysis/sessions/{id}/report` | 전체 요약 + 부위별 리포트 |
| `GET` | `/analysis/reports/latest` | 로그인 사용자 기준 최신 완료 리포트 |
| `GET` | `/analysis/sessions/{id}/metrics` | 세션 상세 측정값 |
| `GET` | `/analysis/metrics/trends` | 지표별 시계열 추이 |
| `GET` | `/recommendations/sessions/{id}` | 저장된 추천 결과 |

### Frontend (Streamlit, `:8501`)

- 촬영/업로드 → 분석 → 리포트 → 추천 흐름, `app.py`에서 직접 라우팅
- 수치 표시 정책 — `measured_value`가 있으면 "측정값", 없으면 `predicted_value`를 "예측값"으로 표시하고, 둘 다 없으면 등급만 표시
- `session_id` · `image_id` · `raw_part_name` · `model_name` 같은 내부 값은 화면에 노출하지 않음

## 12. 트러블슈팅

### 12.1 정확도 0.673, macro-F1 0.303 — 불균형에 속을 뻔했다

**문제**
초기 학습에서 accuracy가 0.673으로 나쁘지 않아 보였습니다. 그런데 macro-F1은 0.303이었습니다. 다수 등급만 맞히고 희소 등급은 거의 예측하지 못하는 모델이었습니다.

**해결**

- 기준 지표를 accuracy에서 **macro-F1으로 교체**하고, 조기 종료도 macro-F1 기준으로 변경
- `FocalLoss`(γ 조정)로 쉬운 다수 클래스의 손실 기여를 낮춤
- `WeightedRandomSampler`로 배치 단위 클래스 균형 확보
- 클래스별 분포를 학습 시작 시 로그로 출력해 **매 실험마다 눈으로 확인**

**결과**
지표가 실제 성능을 반영하게 됐고, 이후 실험의 개선/악화를 신뢰할 수 있게 됐습니다.

---

### 12.2 균형 보정을 했더니 성능이 오히려 떨어졌다

**문제**
5등급을 3등급으로 병합해 macro-F1 0.665를 얻은 뒤, 여기에 데이터 균형 보정을 추가로 적용했습니다. 더 좋아질 것이라 예상했지만 결과는 **0.665 → 0.644, accuracy 0.728 → 0.703**으로 하락했습니다. (수치는 §6의 출처 기준)

**해결**

- 등급을 이미 3개로 합친 시점에서 분포가 상당히 평탄해졌고, 그 위에 균형 보정을 또 얹으면 **다수 클래스의 정상 신호까지 깎인다**고 판단
- 보정을 되돌리고 3등급 ordinal 설정을 기준선으로 확정
- 실패한 실험을 지우지 않고 조건·수치와 함께 기록

**결과**
"불균형 대응은 무조건 좋다"는 가정을 버리고, **문제 정의를 바꾼 뒤에는 대응 강도도 다시 재야 한다**는 기준을 얻었습니다.

---

### 12.3 같은 사람의 사진이 train과 val에 동시에 들어갈 뻔했다

**문제**
한 사람당 여러 각도·장비로 촬영된 데이터셋입니다. 이미지 단위로 무작위 분할하면 같은 얼굴이 학습과 검증에 모두 들어가 검증 점수가 부풀려집니다.

**해결**

- 사람(`id`) 단위로 그룹을 묶어 분할하도록 `rebalance_split.py` 작성
- 단순 그룹 분할만 하면 희소 등급이 한쪽에 몰려 검증이 불가능해지므로, **희소 클래스를 먼저 덮도록 그룹을 선택**하는 방식으로 구성
- 메타데이터 CSV에 `id`를 필수 컬럼으로 두어 이후에도 누수 여부를 검증 가능하게 함

**결과**
검증 점수가 실제 일반화 성능을 반영하게 됐고, 6.3의 실험 비교가 의미를 갖게 됐습니다.

---

### 12.4 모델 출력을 서비스로 옮길 때 등급과 측정값이 섞일 뻔했다

**문제**
모델은 회귀 예측값을, 장비/AI-Hub JSON은 측정 수치를 줍니다. 둘 다 실수라 한 컬럼에 담기 쉬운데, 그러면 나중에 **이 값이 예측인지 측정인지 알 수 없습니다.** 단위와 범위도 다릅니다.

**해결**

- `grade_value`(등급) · `predicted_value`(모델 예측) · `measured_value`(장비/JSON 측정)를 **별도 컬럼**으로 분리
- 두 회귀 필드는 `Optional`로 두어 이 필드를 모르는 이전 버전 AI 서버와도 호환
- 프론트는 `measured_value` → `predicted_value` → `grade_value` 순으로 **라벨을 다르게 붙여** 표시
- 부위 미검출 시 값도 버리지 않고 `bbox_source`로 신뢰도를 구분 저장

**결과**
학습 단계에서 정리한 분류/회귀 구분(§5.3)이 DB 스키마와 화면 표시까지 일관되게 이어졌습니다.

## 13. 회고

이 프로젝트에서 가장 크게 배운 것은 **성능이 안 나올 때 어디를 먼저 봐야 하는가**였습니다. 처음에는 하이퍼파라미터와 증강을 바꾸는 데 시간을 썼는데, 실제로 성능을 끌어올린 것은 **라벨 정의를 5등급에서 3등급으로 바꾼 것**이었습니다. macro-F1이 0.303에서 0.665로 올라간 개선은 모델이 아니라 문제 정의에서 나왔습니다. 모델을 바꾸기 전에 데이터와 라벨을 의심하는 순서를 몸으로 익혔습니다.

두 번째는 **지표를 잘못 고르면 실험 전체가 무의미해진다**는 것이었습니다. accuracy 0.673 / macro-F1 0.303은 같은 모델의 두 얼굴입니다. 불균형 데이터에서 accuracy만 보고 있었다면 "잘 되고 있다"고 착각한 채 계속 갔을 겁니다. 기준 지표를 macro-F1으로 바꾼 뒤에야 이후 실험들의 개선과 악화를 신뢰할 수 있었습니다.

세 번째는 **실패한 실험도 자산이라는 것**입니다. 균형 보정을 추가했다가 성능이 떨어져 되돌린 실험(0.665 → 0.644)은 결과만 보면 버릴 기록이지만, "등급 병합 이후에는 추가 균형 보정이 역효과"라는 판단 근거로 남았습니다. 그리고 이런 진단이 쌓여 **ResNet-50의 한계를 백본 문제로 규정하고 DINOv3 전환을 결정하는 근거**가 됐습니다.

마지막은 **모델과 서비스 사이가 생각보다 넓다는 것**이었습니다. 학습이 끝나도 출력을 어떤 구조로 넘길지, 등급과 측정값을 어떻게 구분해 저장할지, 검출 실패를 어떻게 표시할지를 정하지 않으면 서비스에 붙지 않습니다. `chin_moisture`처럼 **학습 라벨에 없어 항상 0이던 지표를 E2E 검증에서 잡아내 제거한 경험**이 특히 그랬습니다. 값이 비어 있는 것과 값이 0인 것은 다르고, 그 차이를 스키마로 표현하지 않으면 사용자에게 거짓 정보가 나갑니다.

아쉬운 점은 **제가 학습한 모델을 최종 서비스에 연결하지 못한 것**입니다. 운영 추론은 팀이 전환한 DINOv3 모델이 담당하고, 제 파이프라인은 실험 설정과 진단 기록으로 남았습니다.

프로젝트가 끝난 뒤 원본 데이터를 직접 받아 다시 돌린 것(§6.5~6.10, §7.4~7.6)에서 배운 것은 조금 다릅니다. **먼저, 제가 맞다고 믿은 전처리 규칙이 틀려 있었습니다.** 각도 코드를 반대로 읽어 가장 선명한 크롭을 버리고 있었고, 이건 학습을 아무리 돌려도 지표로는 드러나지 않는 종류의 오류였습니다. 라벨 10만 건의 bbox 통계와 대조 시트로 눈으로 확인하고 나서야 보였습니다 — **모델을 의심하기 전에 데이터를, 데이터를 의심하기 전에 내가 쓴 필터를** 먼저 봐야 한다는 걸 이때 배웠습니다.

**둘째, 제약이 설계를 만들었습니다.** GPU가 없어 미세조정이 불가능했기 때문에 백본을 얼리고 특징을 캐싱하는 구조를 택했고, 그 덕에 실험 1회가 수 초로 줄어 23개 조건을 하루에 비교할 수 있었습니다. 공교롭게도 팀이 DINOv3에서 택한 `FROZEN + CACHING`과 같은 발상이었습니다.

**셋째, "백본의 한계"라는 진단이 사실인지 이제 수치로 답할 수 있습니다.** 파라미터 수를 맞춘 DINOv3 ViT-S로 바꾸자 색소침착 QWK가 0.640 → 0.736으로, 디카 학습 → 폰 검증 성능이 0.403 → 0.505로 올랐습니다. 당시에는 "그럴 것 같다"로 넘긴 판단을 **같은 조건에서 직접 확인해 근거로 바꾼 것**이, 이 프로젝트에서 제가 마지막으로 얻은 것입니다.

**넷째, 실험이 빨라지면 새로운 종류의 오류가 생깁니다.** head 학습이 수 초로 끝나니 조건을 수십 개 비교할 수 있었는데, 그 편리함 때문에 **각 수치가 시드 운을 얼마나 타는지를 한참 동안 재지 않았습니다.** 뒤늦게 같은 조건을 12회 돌려 보니 표준편차가 0.0074였고, 그 시점에 이미 써 둔 비교 중 일부는 노이즈와 구분되지 않는 것이었습니다(모공 3등급의 CORAL vs CE 차이 0.006). 결론 하나를 철회하고, 0.02 미만 차이는 주장하지 않는다는 기준을 §6.8에 명시했습니다. 실험을 많이 돌리는 것과 믿을 수 있게 돌리는 것은 다른 문제였습니다.

**다섯째, 예측이 빗나가는 것이 실험의 실패는 아닙니다.** 볼에서 종횡비 왜곡이 성능을 깎는 것을 확인한 뒤, 눈가는 왜곡이 2배이니 피해도 더 클 것이라고 두 번이나 문서에 적었습니다. 눈가 특징을 뽑아 재보니 **차이가 없었고, 방향조차 일정하지 않았습니다.** 확장 작업의 목적이 그 예측의 검증이었으니 목적은 달성된 셈입니다 — 결과가 반대였을 뿐입니다. 이 경험 이후 문서에 "~일 것으로 추정됩니다"와 "~로 확인됐습니다"를 구분해 쓰기 시작했습니다.

같은 맥락에서, 서비스의 "한쪽 눈이 측정되지 않는다"는 현상도 가설 세 개를 세워 전부 반증한 뒤에야 원인을 찾았습니다(§7.4). 검출기는 정상이었고, 데이터셋이 가려진 쪽 눈가에 라벨을 붙이지 않았을 뿐이었습니다. **고치기 전에 먼저 재는 순서**가 세 번의 헛수고를 막았습니다.

그리고 아쉬웠던 것 하나는 해결했습니다 — run별 결과가 로컬 체크포인트에만 남던 문제는, `results/head_experiments.csv`에 조건 · 지표 · 시드를 한 줄씩 누적하는 방식으로 정리했습니다(203건).

## 14. 고도화 방향

### Phase 1. 실험 기록 자동화 — 완료

`train_head.py`가 모든 실행을 `results/head_experiments.csv`에 누적합니다 — 조건 · 지표 · 기기별 성능 · 소요 시간 · **시드**까지 203건. 남은 것은 두 가지입니다. `train.py`(전체 미세조정 경로)에도 같은 기록을 붙이는 것, 그리고 **각 조건을 여러 시드로 자동 반복해 평균±sd를 한 줄로 남기는 것**입니다. 지금은 5시드 비교를 수동으로 돌리고 집계도 따로 합니다.

### Phase 2. 볼 부위 모델의 서비스 연결

학습한 모공·색소침착 분류 모델을 추론 서버 라벨 레지스트리에 등록합니다. 추론 계약(§7.1)이 고정돼 있으므로 **백엔드 수정 없이** 연결 가능합니다.

### Phase 3. 지표별 임계값 확정

`predicted_value` · `measured_value`의 값 범위와 방향성(값이 클수록 좋은지 나쁜지)이 확정되면, 현재 등급 기반인 severity를 연속값 기준으로 더 정교하게 계산할 수 있습니다. 현재는 분포를 산출할 세션 수가 부족해 후보값만 문서에 기록해 두었습니다.

### Phase 4. 촬영 기기 도메인 갭 해소 — 부분 완료

열화 증강(§6.8-(5))으로 디카 학습 → 폰 검증 성능이 0.518 → 0.531(모공), 0.573 → 0.595(색소침착)로 올랐고 시드 분산이 절반이 됐습니다. **다만 기기 간 격차 자체는 그대로**입니다.

남은 방향은 두 가지입니다. 하나는 **열화 파라미터를 임의로 정하지 않고 실제 폰/디카 이미지 쌍의 통계(주파수 스펙트럼, 노이즈 분포)에 맞추는 것**이고, 다른 하나는 **기기 라벨을 도메인으로 쓰는 적대적 학습(DANN 계열)** 으로 기기 정보를 특징에서 직접 제거하는 것입니다. 후자는 head만 학습하는 현재 구조에서도 gradient reversal 레이어 하나로 시도할 수 있습니다.

### Phase 5. 백본 스케일업 검증

DINOv3 ViT-S/16(21.6M)에서 이득이 확인됐으므로, ViT-B/16(86M)에서 얼마나 더 오르는지가 다음 질문입니다. CPU로는 특징 추출에 2시간 이상 걸려 보류했고, GPU가 확보되면 같은 프로토콜로 바로 비교할 수 있습니다.

### Phase 6. 부위 검출률 개선 — 원인 규명 완료

한쪽 눈가가 측정되지 않는 원인은 **검출기 결함이 아니라 데이터셋이 가려진 쪽에 라벨을 붙이지 않은 것**으로 확인됐습니다(§7.4). 추정값 표시(§7.6)와 정면 판정 임계값(0.05)까지 나왔으므로, 남은 것은 **업로드 시점 재촬영 안내**의 문구와 흐름을 정하는 일입니다.

정면 판정의 알려진 약점은 **아래를 본 사진(angle 2)에서 66.7%** 라는 점입니다. 미간이 두 볼 중점에서 벗어난 정도만 보는 지금 지표에 **y축 항을 추가**하면 개선될 것으로 보이며, 보정 스크립트(`frontality_calibration.py`)가 있으므로 같은 270장으로 바로 재측정할 수 있습니다.

### Phase 7. 나머지 부위로의 확장

눈가까지 확장하며 `crop.py`를 부위 테이블 기반으로 일반화했으므로(§6.9), 이마 · 미간 · 입술 · 턱은 테이블에 항목을 추가하는 것으로 시작할 수 있습니다. 다만 **등급 범위가 부위마다 다릅니다** — 미간 0~2, 이마 색소 0~3, 이마 주름 · 입술 0~4, 눈가 · 볼 · 턱 0~5(눈가 주름은 0~6). 3등급 병합의 척도 위치를 부위마다 다시 정해야 하고, 이때 **경계를 macro-F1으로 고르지 않는다**는 §6.9의 원칙이 그대로 적용됩니다.

### Phase 8. 분류에서 회귀로

눈가와 볼에는 장비 측정값이 함께 있습니다 — 눈가는 `wrinkle_l_eye_Ra` · `_Rmax` 등 거칠기 파라미터, 볼은 `pore_count_*` · `*_moisture`. 지금까지는 전문가 진단 등급(`annotations`)만 썼지만, **캐싱된 특징 위에 회귀 헤드를 하나 더 얹는 것으로 분류와 회귀를 같이 학습**할 수 있습니다. 팀이 DINOv3에서 택한 "분류 + 개수 + 회귀" 방향과 같고, 코드 변경은 head와 손실 함수에 국한됩니다.
