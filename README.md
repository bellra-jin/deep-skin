## 데이터 전처리 · 부위별 등급 분류 모델 · AI 추론 연동

> 얼굴 이미지 한 장에서 부위별 피부 상태를 등급으로 정량화하고, 그 결과를 성분 추천까지 연결하는 서비스입니다.

## 3. 문제 정의

**라벨 경계가 모호합니다.** 인접 등급의 차이를 사람도 일관되게 구분하기 어렵고, 희소 등급은 표본이 부족합니다.

**부위마다 크롭 크기와 비율이 다릅니다.** 고정 비율로 자르면 어떤 각도에서는 경계가 잘리고 어떤 각도에서는 배경이 과하게 들어옵니다.

### 설계 원칙

| 원칙 | 무엇으로 강제되는가 |
|---|---|
| accuracy가 아니라 macro-F1으로 판단한다 | 조기 종료 기준을 macro-F1으로 고정 (§6.1) |
| 같은 사람이 train/val에 동시에 들어가지 않는다 | 사람(id) 단위 그룹 분할 (§5.2) |
| 분류 라벨과 회귀 측정값을 섞지 않는다 | `annotations` / `equipment`를 스키마 단계에서 분리 (§5.3) |
| 추정한 값을 실측값처럼 내보내지 않는다 | `bbox_source`를 리포트에 노출 (§7.5) |

## 5. 데이터 전처리 파이프라인

### 5.1 부위별 크롭과 각도 필터

AI-Hub 이미지는 여러 촬영 각도로 찍혀 있고, **부위마다 가려지는 각도가 다릅니다.** 가려진 부위를 학습에 넣으면 모델은 그 부위가 아닌 것을 그 부위라고 배웁니다.

| 부위 | 사용 각도 | 제외 각도 |
|---|---|---|
| 왼쪽 볼·눈가 | 정면 · 위 · 아래 · **R15° · R30°** · 왼쪽 측면 | L15° · L30° |
| 오른쪽 볼·눈가 | 정면 · 위 · 아래 · **L15° · L30°** · 오른쪽 측면 | R15° · R30° |

> 이 표는 **원본 라벨 10만 건의 bbox 통계로 검증해 한 번 뒤집힌 결과**입니다. 발견 경위는 §6.3에 있습니다.
>
> 좌/우는 **관찰자(이미지) 기준**입니다 — `왼쪽 볼`은 이미지 왼쪽에 있고, 이는 피사체의 오른쪽 얼굴입니다.

크롭 규칙은 세 가지입니다. 파일명이 아니라 **JSON 내부 `facepart` 값으로 부위를 확정**하고, bbox에 margin을 적용해 주변 맥락을 남기며, 최소 해상도 규칙으로 저품질 크롭을 걸러냅니다.

### 5.2 ID 그룹 분할

한 사람당 여러 각도·장비로 촬영된 데이터셋이라 **랜덤 분할은 곧 데이터 누수**입니다. 사람(id) 단위로 묶되, 무작위가 아니라 **희소 클래스 커버리지를 우선하는 그리디 선택**으로 val을 구성했습니다. 사람 단위로만 나누면 희소 등급이 한쪽에 몰려 검증이 불가능해집니다.

### 5.3 분류와 회귀를 섞지 않는다

라벨 JSON에는 **이름이 같고 의미가 다른 두 값**이 있습니다.

| JSON 영역 | 의미 | 학습 유형 |
|---|---|---|
| `annotations` | 전문가 진단 등급 | Classification (`l_cheek_pore` = 0~5 등급) |
| `equipment` | 장비 측정 수치 | Regression (`l_cheek_pore` = 측정값) |

혼동한 채 학습하면 결과 전체가 무의미해지므로 코드를 쓰기 전에 문서로 고정했습니다. 이 구분은 백엔드 DB 설계까지 그대로 이어집니다(§7.2).

## 6. 등급 분류 모델 학습

담당 부위는 **양쪽 볼(facepart 5·6)**, 예측 대상은 모공·색소침착 등급입니다.

> **수치 출처 구분** — 6.1은 팀 발표 자료의 수치(백본 미세조정 기준)이고, **6.2부터는 개인 재실험 수치**(백본 동결 프로브, AI-Hub 원본 분할, 각도 필터 수정 후)입니다. 학습 방식·분할·전처리가 달라 **두 수치를 직접 비교하면 안 됩니다.**

### 6.1 팀 단계 — 모델보다 라벨 정의를 바꾼 것이 컸다

```text
backbone   ResNet-50 (ImageNet)        head   2048 → 512 → num_classes
optimizer  AdamW                       stop   macro-F1 기준 조기 종료
```

백본은 freeze / unfreeze를 전환할 수 있게 분리하고, 실험 설정은 JSON으로 빼 조건만 바꿔 재현할 수 있게 했습니다.

첫 결과가 accuracy 0.673 / macro-F1 0.303이었습니다. 불균형 데이터에서 accuracy는 다수 클래스만 맞혀도 높게 나오므로, 이 격차는 **희소 등급을 거의 못 맞히고 있다**는 뜻입니다. 기준 지표를 macro-F1으로 고정한 뒤부터 이후 실험의 개선·악화를 신뢰할 수 있었습니다.

성능을 실제로 끌어올린 것은 손실 함수가 아니라 **라벨 정의를 바꾼 것**입니다. 인접 등급 경계가 모호하고, 서비스가 보여줄 단위도 결국 "양호/보통/주의"이기 때문입니다.

| 실험 조건 | macro-F1 | accuracy |
|---|---:|---:|
| 3등급 · ordinal optimized | **0.665** | **0.728** |
| 3등급 · balanced 보정 | 0.644 | 0.703 |
| 3등급 · quick check | 0.303 | 0.673 |

반대로 **추가 균형 보정은 성능을 떨어뜨려**(0.665 → 0.644) 되돌렸지만, "해봤는데 안 됐다"는 근거와 함께 남겼습니다.

여기서 곡선이 멈췄습니다. EPOCH 11의 best(0.665) 이후 train/val 간격이 계속 벌어지는 과적합 패턴이라, 하이퍼파라미터를 더 만지는 대신 **백본 자체의 한계**로 진단했고 팀은 이 진단을 근거로 DINOv3 멀티태스크 구조로 전환했습니다.

| | ResNet-50 | DINOv3 (팀 전환 결과) |
|---|---|---|
| 사전학습 | 140만 장 · 지도학습 | 17억 장 · 자기지도학습 |
| 백본 처리 | Fine-tuning | Frozen + Caching |
| 처리 부위 | 부위별 개별 모델 | 8개 부위 통합 |

**팀 단계에서 제 기여는 전환 결정의 근거가 된 한계 진단과 실험 기록까지입니다.**

### 6.2 포크 이후 — 원본으로 다시 검증했다

팀 프로젝트가 끝난 뒤 저장소를 포크해 **AI-Hub 원본(22.6GB)을 직접 받아** 볼 부위 파이프라인을 처음부터 다시 돌렸습니다. 전처리가 의도대로 동작하는지 원본으로 확인하고, §6.1의 "백본의 한계"라는 진단이 사실인지 같은 조건에서 재는 것이 목적이었습니다.

작업 환경은 **CUDA 미지원 노트북(물리 4코어 CPU)** 입니다. 이 제약이 §6.4의 설계를 결정했습니다.

### 6.3 각도 필터가 뒤집혀 있었다

크롭 결과를 눈으로 보기 전에는 필터가 맞는지 알 수 없다고 판단해, 부위·각도별 크롭을 샘플링해 대조 시트를 만드는 것부터 했습니다. 결과는 예상과 정반대였습니다.

**각도 코드는 "얼굴이 도는 방향" 기준이지, "어느 쪽이 보이는가" 기준이 아니었습니다.** 얼굴이 오른쪽으로 돌면 카메라 정면으로 오는 것은 **왼쪽 볼**입니다. 원래 필터는 이걸 반대로 읽어, 가장 선명한 각도를 버리고 가장 납작한 각도를 학습에 넣고 있었습니다.

라벨 JSON 100,386건의 bbox 통계로 확인했습니다. 아래는 왼쪽 볼 크롭의 가로/세로 비 중앙값으로, **클수록 부위가 정면으로 온 것**입니다.

| 각도 | 5 (R15°) | 6 (R30°) | 8 (측면) | 3 (L15°) | 4 (L30°) |
|---|---:|---:|---:|---:|---:|
| 가로/세로 비 | **1.16** | **1.39** | **1.32** | 0.52 | 0.44 |
| 기존 필터 | 제외 | 제외 | 제외 | 사용 | 사용 |

오른쪽 볼은 정확히 거울상이었습니다. 필터를 뒤집고, 품질 임계값도 감이 아니라 **15,444개 샘플의 백분위**에서 산출했습니다(`min_width` 150 → 0.48% 제거).

| | 수정 전 | 수정 후 |
|---|---:|---:|
| train 크롭 | 10,300여 장 | **15,295장 (+48%)** |
| 스마트폰·패드 비중 | 33% | **44%** |
| 크롭 오류 | — | 0건 |

데이터가 1.5배로 늘었을 뿐 아니라 **서비스 입력과 같은 기기의 비중**이 올랐습니다.

덧붙이면, 대조 시트를 보고 처음에는 "letterbox 패딩을 넣어야 한다"고 판단했습니다. 그런데 `dataset.py`를 다시 읽어 보니 **이미 들어 있었습니다.** 찌그러져 보인 것은 제 뷰어가 정사각형으로 리사이즈했기 때문이었습니다. **문제를 발견했다고 생각했을 때 먼저 기존 코드를 다시 읽는** 순서를 여기서 배웠습니다.

### 6.4 GPU 없이 실험을 반복하는 구조

CPU만으로 ResNet-50을 전체 미세조정하면 **에폭당 1시간**을 넘습니다. 조건을 바꿔 비교하는 것 자체가 불가능합니다. 그래서 **백본을 얼리고 특징을 한 번만 뽑아 캐싱**했습니다. 공교롭게도 팀이 DINOv3에서 택한 `FROZEN + CACHING`과 같은 발상입니다.

```text
                 1회 (수십 분)                    반복 (수 초)
크롭 이미지 ──► [동결 백본] ──► .npz 특징 캐시 ──► [얕은 head 학습] ──► 지표
                                    └ 손실함수 · 등급 병합 · 샘플러 · 평가 프로토콜을 바꿔 재사용
```

| | 소요 |
|---|---:|
| 특징 추출 (train 15,295장) | 23~47분 |
| **head 학습 1회 (60에폭)** | **5~22초** |

전처리는 학습과 동일하게 맞추고, 캐싱과 상충하는 증강 대신 **좌우반전 특징을 함께 저장**해 head 학습 때 선택하도록 했습니다.

### 6.5 실험 결과 — 무엇이 듣고 무엇이 안 들었나

> 아래 표는 별도 표기가 없으면 **단일 시드**입니다. 시드 산포와 그로 인한 결론 철회는 §6.7에 있습니다. **0.02 미만의 차이로는 우열을 주장하지 않습니다.**

**(1) 불균형 보정 3종은 전부 실패했다**

모공은 6등급 중 등급 2가 **60.7%** 입니다. 데이터를 1.5배 늘린 뒤에도 비율이 그대로였다는 것은 **불균형이 필터 부작용이 아니라 라벨 자체의 성질**이라는 뜻입니다.

| 모공 6등급 · ResNet-50 | 기준선(CE) | Focal | 가중샘플러 | 클래스가중치 |
|---|---:|---:|---:|---:|
| macro-F1 | 0.370 | 0.373 | 0.357 | 0.299 |

Focal은 사실상 무의미하고 나머지 둘은 **오히려 떨어뜨립니다.** 손실 함수로 해결할 문제가 아니었습니다.

**(2) 문제를 고친 것은 등급 병합이었다**

| ResNet-50 | 6등급 | 3등급 |
|---|---:|---:|
| 색소침착 macro-F1 | 0.366 | **0.606** |
| 모공 macro-F1 | 0.370 | **0.545** |

다만 **검증 세트에 모공 등급 5가 0건**이라 6등급 macro-F1은 구조적으로 낮게 나옵니다. 존재하는 5개 클래스로만 평균 내면 0.370이 아니라 0.444입니다. **개선은 실재하지만 표에 보이는 것만큼 크지는 않습니다.**

**(3) 백본을 바꾸면 오른다 — 그것도 같은 크기에서**

§6.1의 진단을 같은 프로토콜로 검증했습니다. 비교 대상은 DINOv3 ViT-S/16 (21.6M), ResNet-50은 25.6M이라 **파라미터는 오히려 DINOv3가 적습니다.** "모델을 키워서 이겼다"가 아니라 사전학습 방식의 차이만 남는 비교가 되도록 고른 것입니다.

| 과제 | 백본 | macro-F1 | QWK | 폰 F1 |
|---|---|---:|---:|---:|
| 색소침착 3등급 | ResNet-50 | 0.606 | 0.685 | 0.578 |
| | **DINOv3** | **0.657** | **0.742** | **0.630** |
| 모공 3등급 | ResNet-50 | 0.545 | 0.402 | 0.479 |
| | DINOv3 | 0.563 | 0.436 | 0.499 |
| 색소침착 6등급 | ResNet-50 | 0.366 | 0.640 | 0.273 |
| | **DINOv3 + CORAL** | **0.429** | **0.736** | 0.360 |

주목한 것은 QWK입니다. 색소침착 6등급에서 macro-F1은 +0.03인데 QWK는 0.640 → 0.736입니다. QWK는 "몇 등급 차이로 틀렸는가"에 가중치를 주므로, **DINOv3 특징은 맞고 틀림보다 등급의 순서를 훨씬 잘 담고 있다**는 뜻입니다.

CORAL(서수 손실)의 거동도 같은 해석을 뒷받침합니다 — **ResNet-50 위에서는 6등급 macro-F1을 0.378 → 0.356으로 떨어뜨리지만, DINOv3 위에서는 0.400 → 0.429로 올립니다.** 부호가 반대라는 점이 핵심입니다. 서수 손실은 특징이 이미 등급 순서를 담고 있을 때만 작동합니다.

**(4) 촬영 기기가 바뀌면 성능이 떨어진다**

학습 데이터는 디지털카메라 비중이 높은데 **서비스 입력은 스마트폰**입니다. 디카로만 학습해 폰으로만 검증하는 평가 모드를 넣었습니다.

| 디카 학습 → 폰 검증 (3등급) | ResNet-50 | DINOv3 |
|---|---:|---:|
| 모공 macro-F1 | 0.403 | **0.505** |
| 색소침착 macro-F1 | 0.523 | **0.568** |

**(5) 열화 증강 — 평균보다 분산이 움직였다**

디카 이미지를 폰 촬영에 가깝게 열화시킨(다운스케일 → 블러 → JPEG 재압축) 특징을 함께 캐싱해 학습에 섞었습니다. 1차 파라미터는 효과가 없었는데, 원인이 분명했습니다 — 크롭이 어차피 256px로 줄어드니 **1/2 다운스케일이 최종 리사이즈에 흡수**됐습니다(열화 전후 특징 코사인 유사도 0.995). 강도를 올린 뒤에야 신호가 나왔습니다.

| 5시드 짝지은 비교 | 기준선 | 열화 증강 | 차이 | 승 |
|---|---:|---:|---:|:--:|
| 모공 · 디카 학습 → 폰 검증 | 0.518 (sd .013) | **0.531** (sd .006) | +0.014 | 4/5 |
| 색소침착 · 디카 학습 → 폰 검증 | 0.573 (sd .018) | **0.595** (sd .006) | +0.022 | 4/5 |

**평균 상승폭보다 표준편차가 절반으로 준 것이 더 일관된 신호입니다.** 성능을 크게 끌어올렸다기보다 **학습을 안정화시켰다**고 읽는 편이 맞습니다.

**(6) 기기 정보를 특징에서 직접 제거해 봤다 — 프로토콜에 따라 갈린다**

증강이 절반만 먹혔으므로, 다른 접근으로 **특징에서 기기 정보를 지우는 것**(gradient reversal, DANN)을 시도했습니다.

먼저 잡아야 했던 함정이 있습니다. 처음 구현은 GRL을 캐싱된 원본 특징에 걸었는데, 백본이 동결돼 있어 그 지점 상류에는 **학습 파라미터가 하나도 없습니다.** 도메인 손실이 5에폭 만에 0.001로 붕괴하는 것으로 드러났고, 분류기를 `head.trunk` 출력에 연결하자 λ 램프를 따라 0.034 → 0.884로 반등했습니다. **이걸 못 잡았으면 "DANN도 안 됐다"가 거짓 음성이 됐을 겁니다.**

| 모공 3등급 (5시드) | 기준선 | DANN λ=1.0 | 열화 증강 | 증강+DANN |
|---|---:|---:|---:|---:|
| 디카 학습 → 폰 검증 | 0.518 | 0.517 (1/5) | **0.531** (4/5) | 0.531 (5/5) |
| 전체 검증 · 폰 subset | 0.467 | 0.507 (5/5) | 0.480 (4/5) | **0.529** (5/5) |
| 전체 검증 · 디카−폰 격차 | 0.097 | 0.061 | 0.080 | **0.036 (−63%)** |

**비지도(디카만 라벨)에서는 실패**했고, **전체 검증(폰도 라벨 사용)에서는 격차가 63% 줄었습니다.** 디카는 0.5646 → 0.5655로 유지되므로 폰만 끌어올린 것이 아니라 격차 자체가 줄었습니다.

차이는 학습에 폰 라벨이 들어가느냐입니다. 전자는 순수 비지도 도메인 적응이고, 후자는 도메인 적응이라기보다 기기 불변 표현 학습입니다. 따라서 **63%는 이 조건에서의 값이지 비지도 적응 성능이 아닙니다** — 두 수치를 섞어 쓰면 사실과 다릅니다.

### 6.6 부위 확장 — 볼의 결론은 눈가로 전이되는가

볼과 좌우 구조가 같은 **눈가(facepart 3·4)** 로 확장해, 위 결론들이 부위가 바뀌어도 성립하는지 확인했습니다. `crop.py`를 부위 테이블 기반으로 일반화했고, 볼 산출물은 재생성하지 않았습니다(회귀 macro-F1 0.5820 동일).

**문서 오류가 또 나왔습니다** — `perocular_wrinkle`은 문서상 0~5인데 **실제로는 0~6(7등급)** 입니다. 등급 6이 train 1,471건 존재합니다.

| 볼에서의 결론 | 눈가에서 | 판정 |
|---|---|---|
| 등급 병합이 크게 이득 | 7등급 0.393 → 3등급 **0.624** | 전이됨 |
| CORAL이 QWK를 올린다 | 7등급 QWK 0.840 → **0.852** / 3등급은 0.818 → 0.813 | **조건부** |
| 기기가 바뀌면 성능이 떨어진다 | 전체 0.624 → 디카 학습·폰 검증 **0.470** | 전이됨 |

**CORAL에 조건이 붙습니다.** 3등급에서는 임계값이 2개뿐이라 서수 구조에서 얻을 정보가 거의 없습니다. §6.5에서 "특징이 순서를 담고 있을 때만 CORAL이 듣는다"고 썼는데, **라벨 쪽에도 같은 조건이 붙는 셈**입니다.

**병합 경계를 지표로 고르면 안 됩니다.** 7등급을 3등급으로 묶을 때 분포를 균등하게 맞춘 경계(0-1/2-3/4-6)는 macro-F1 0.749, 볼과 척도 위치를 맞춘 경계(0-1/2/3-6)는 0.624입니다. 후자가 0.125 낮지만, 이 차이의 상당 부분은 macro-F1이 균형 잡힌 클래스를 유리하게 평가하는 성질에서 옵니다. 라벨 정의를 바꿔서 그 정의가 결정하는 지표를 최대화하는 것은 순환 논리이므로, **더 낮은 0.624를 채택**했습니다.

**종횡비 가설은 기각됐습니다.** §6.5에서 추론 엔진의 강제 정사각형 리사이즈가 볼 성능을 깎는 것을 확인했고, 눈가는 bbox 종횡비가 0.38~0.43(볼 0.75)이라 **왜곡이 2배 이상이므로 피해가 더 클 것**으로 예측했습니다. 이번 확장의 주된 목적이 그 검증이었습니다.

| ResizeAndPad → 강제 정사각형 | 볼 | 눈가 |
|---|---:|---:|
| 전체 검증 | **−0.0134** (0/5) | +0.0045 (3/5) |
| 폰 검증 | **−0.0317** (0/5) | −0.0058 (3/5) |

**예측과 반대입니다.** 눈가에서는 둘 다 시드 산포 안이고 방향조차 일정하지 않습니다. 전처리는 `ResizeAndPad`로 통일하되, **"종횡비 왜곡이 성능을 깎는다"를 일반 명제로 쓰면 안 됩니다** — 볼에서는 깎고 눈가에서는 차이가 없습니다.

### 6.7 측정하지 않은 것은 주장하지 않는다

**시드 산포 — 결론 하나를 철회했다.** head 학습이 수 초로 끝나 조건을 수십 개 비교할 수 있었는데, 그 편리함 때문에 각 수치가 시드 운을 얼마나 타는지를 한참 재지 않았습니다. 동일 조건 12회의 표준편차는 **0.0074**(범위 0.5632~0.5870), 표본이 410건뿐인 기기 분리 평가에서는 0.013~0.018이었습니다. 동일 시드 2회 실행은 완전히 같은 값을 내므로 재현성 문제가 아니라 순수한 초기화·샘플링 민감도입니다.

이후 **0.02 미만 차이로는 우열을 주장하지 않는다**는 기준을 세웠고, 그에 따라 "모공 3등급에서 CORAL이 CE보다 낫다"(차이 0.006)를 **철회**했습니다.

**비교 조건을 고정하지 않으면 측정이 아니다.** 두 번 같은 함정에 빠질 뻔했습니다. 크롭 폭 임계값을 train/val 양쪽에 걸어 임계값마다 검증셋이 달라진 경우 — 150이 +0.006으로 개선처럼 보였지만 검증셋을 고정하니 −0.006이었습니다. 그리고 열화 증강 효과를 단일 시드 기준선(0.505)과 비교한 경우 — 그 기준선은 시드 운이 나쁜 draw였고, 정직한 수치는 **+0.030이 아니라 +0.014**였습니다.

**교란 요인은 배제하고 넘어간다.** AI-Hub는 각도와 기기가 독립이 아닙니다(디카 0~6, 패드·폰 0·7·8). 디카로만 학습하면 각도 7·8을 못 보는데 폰 검증 세트의 51%가 그 각도입니다. 검증 세트를 각도로 갈라 확인한 결과 차이가 없어(볼 +0.0026, 눈가 +0.0064) 도메인 갭은 **각도가 아니라 기기 자체**의 것으로 확정했습니다.

**대신 쓸 지표는 검증한 뒤에 쓴다.** §6.8에서 볼 모공 등급이 2 이상부터 측정값과 갈라지는 것을 보고,
"등급 스케일이 길수록 상위 구간이 무의미해지는가" 를 부위 확장으로 확인하려 했습니다. 그런데 이마·미간·턱에는
볼처럼 **같은 이름의 등급↔측정값 짝이 없습니다.** 대신 분류기가 인접 등급을 얼마나 헷갈리는가를
프록시로 쓰기로 하고, 측정값이 있는 볼·눈가에서 두 지표의 순위가 일치하는지부터 재게 했습니다.

**일치하지 않았습니다** — 볼 Spearman +0.200, 눈가 −0.029. 원인은 프록시 정의였습니다. 검증셋에
등급 5 표본이 **0건**이라 그 경계는 분모가 없고, 모델이 예측의 88%를 등급 2에 몰아넣어 상위 등급끼리는
서로 헷갈릴 기회조차 없습니다. "서로 오분류되지 않았다"를 좋은 분리도로 읽는 정의에서는
**둘 다 엉뚱한 곳으로 간 경우가 최고점을 받습니다.**

그래서 **가설 검증을 진행하지 않고 멈췄습니다.** 라벨 상한을 실측해 보니 독립변수도 사라졌습니다 —
문서가 3단계라고 적은 미간이 실제로는 7단계였고(아래 표), **실측 스케일은 5·6·7단계뿐**이라
"짧은 척도" 대조군이 존재하지 않습니다.

**문서를 믿지 않는다.** 라벨 문서에서 오류 **여덟 건**을 찾아 정정했습니다. 전부 코드로는 드러나지 않고 데이터를 세어야만 보였습니다.

| 항목 | 문서 | 실제 | 확인 방법 |
|---|---|---|---|
| bbox 형식 | `[x, y, w, h]` | **`[x1, y1, x2, y2]`** | 문서대로 읽으면 71.2%가 이미지 경계를 벗어남 |
| 패드·폰 각도 | 0~8 | **0·7·8 세 개만** | 각도 1~6의 패드·폰 레코드 0건 |
| 눈가 거칠기 키 | `wrinkle_{l,r}_eye_Ra` | **`{l,r}_perocular_wrinkle_Ra`** | 실제 JSON 키를 전수 집계 |
| **등급 상한 5건** — 눈가·미간·이마 주름 / 이마 색소 / 턱 | 전부 낮게 | **최대 0~6** | 라벨 JSON 112,905건 전수 집계 (**표는 §7.4**) |

**등급 상한이 다섯 개나 틀렸다는 것은 문서 문제로 끝나지 않습니다.** 서비스의 severity 매핑이
이 문서를 근거로 만들어졌기 때문에, 문서에 없는 상위 등급은 **리포트에서 조용히 사라지고 있었습니다**(§7.4).


### 6.8 등급 라벨은 무엇을 잃고 있는가 — 장비 측정값과의 대조

지금까지 학습한 것은 전부 **전문가 진단 등급**(`annotations`)입니다. 그런데 같은 라벨 JSON에는
**장비 측정 수치**(`equipment`)가 함께 있고, §5.3에서 분리해 둔 뒤로 쓰지 않았습니다.

```text
annotations.l_cheek_pore = 2        전문가가 매긴 등급 (0~5)
equipment.l_cheek_pore   = 629.0    장비가 센 모공 개수
                                     ^ 이름이 같고 의미가 다르다
```

결측은 없었습니다 — 볼·눈가 모두 **100%**, 기기별 편차도 없습니다.
(문서 오류가 하나 더 나왔습니다. 눈가 거칠기 키는 문서의 `wrinkle_{l,r}_eye_Ra`가 아니라
**`{l,r}_perocular_wrinkle_Ra`** 입니다.)

#### 등급과 측정값은 낮은 등급에서만 일치한다

전체 Spearman 상관은 0.35~0.48로 "적당히 관련 있다"로 읽힙니다. 그런데 **인접 등급쌍으로 쪼개면
그림이 완전히 달라집니다.** 아래는 두 등급을 측정값만으로 가를 수 있는 확률입니다.

| 볼 모공 인접 등급쌍 | 0 vs 1 | 1 vs 2 | 2 vs 3 | 3 vs 4 | 4 vs 5 |
|---|---:|---:|---:|---:|---:|
| 측정값으로 가를 확률 | **0.913** | 0.785 | **0.560** | 0.592 | 0.603 |

전문가와 장비는 "모공이 거의 없다 / 조금 있다"까지는 강하게 합의하지만, **그 위로는 거의 무관합니다.**
0.560은 동전 던지기(0.5)에 가깝습니다. 눈가도 같은 패턴으로 3·4·5등급 중앙값이 90/100/101로
사실상 구분되지 않습니다.

그리고 **하필 그 지점부터 데이터가 몰려 있습니다** — 등급 2가 전체의 61%입니다.
§3에서 "라벨 경계가 모호하다"고 전제했던 것을, 여기서 **어디서 어떻게 모호한지** 물리량으로 확인한 셈입니다.

#### 등급 병합이 듣는 이유는 물리적 구분 가능성이 아니다

3등급으로 병합하면 측정값과의 상관이 **오히려 내려갑니다**(볼 −0.011, 눈가 −0.055).
병합(0-1 / 2 / 3-5)은 **가장 잘 갈리는 경계인 0 vs 1(0.913)을 없애고**, 거의 무작위인
3~5 경계를 묶습니다. 그런데도 macro-F1은 0.370 → 0.545로 크게 오릅니다.

그러면 **병합이 듣는 이유는 물리적으로 구분 가능한 단위로 묶여서가 아니라 클래스 균형** 때문이고,
상관이 내려간 것이 그 증거입니다. §6.6에서 "병합 경계를 macro-F1으로 고르면 순환 논리"라고
적은 것과 같은 이야기입니다.

#### 이미지에는 등급이 담지 못한 정보가 있다

캐싱된 특징 위에 회귀 헤드를 하나 더 얹었습니다. 특징 재추출은 필요 없고 — 입력 이미지가 같으므로 —
바뀌는 것은 헤드와 손실 함수뿐입니다.

| 타깃 | MAE (원 단위) | R² | Spearman |
|---|---:|---:|---:|
| 볼 모공 개수 | 206.7±8.5 | 0.509±0.035 | **0.768±0.003** |
| 눈가 거칠기 Ra | 3.09±0.02 | 0.531±0.008 | **0.740±0.002** |
| 볼 수분 | 7.75±0.04 | 0.268±0.005 | 0.550±0.002 |

수분만 약합니다. 표면 텍스처와의 연결이 약해 이미지만으로는 한계가 있어 보이는데,
**이건 측정하지 않은 해석입니다.**

여기서 조심할 것이 있습니다. 모델의 ρ 0.768과 전문가 등급의 ρ 0.444를 나란히 놓고
**"모델이 전문가보다 정확하다"고 읽으면 안 됩니다.** 모델은 그 측정값을 맞히도록 학습됐고,
전문가는 애초에 그럴 목적이 아니었습니다. **같은 선에 놓고 비교할 수 없습니다.**

정당한 해석은 이쪽입니다 — **이미지에는 측정값을 상당히 설명하는 정보가 들어 있는데(ρ 0.77),
등급 라벨은 그 정보를 많이 잃고 있습니다(ρ 0.44).**

#### 회귀를 붙여도 분류는 나빠지지 않는다

| 5시드 | 분류 단독 | + 회귀(both) | 차이 |
|---|---:|---:|---:|
| 볼 모공 3등급 | 0.5787±0.0028 | 0.5780±0.0073 | −0.0007 |
| 눈가 주름 3등급 | 0.6244±0.0026 | 0.6242±0.0023 | −0.0002 |

전부 시드 산포 안이라 **서로 방해하지 않습니다** — 회귀 기능을 사실상 공짜로 얻습니다.
다만 **비대칭이 있습니다.** 분류는 회귀에 영향받지 않는데, 회귀는 분류를 붙이면 약간 나빠집니다
(모공 R² 0.509 → 0.482). 회귀 성능이 목적이면 단독이 낫습니다.

## 7. AI 추론 연동

모델이 잘 나와도 **출력을 서비스가 받아 쓸 수 없으면 의미가 없습니다.** 학습과 서비스 사이를 잇는 구간을 맡았습니다.

### 7.1 추론 계약과 응답 파싱

AI 서버가 없어도 백엔드를 개발할 수 있도록 `AI_INFERENCE_MODE`를 mock / remote / multivalue로 분리하고, 응답 스키마를 Pydantic 계약으로 고정했습니다.

응답은 **등급 · 측정값 · 검출 결과를 서로 다른 테이블로 분해**해 저장합니다. §5.3에서 `annotations`와 `equipment`를 분리한 것이 여기까지 이어집니다 — `predicted_value`(모델 예측)와 `measured_value`(장비 측정)를 한 컬럼에 담으면 나중에 구분할 수 없습니다. 부위 검출 여부는 `bbox_source`(`yolo` / `full_image_fallback`)로 남깁니다.

### 7.2 E2E 검증

업로드부터 화면까지 전 구간을 한 번에 검증했습니다. 이 과정에서 **모델이 추론하지 않아 항상 0으로 채워지던 지표(`chin_moisture`)를 발견해 응답과 저장 대상에서 제거**했습니다. 값이 있는 것처럼 보이지만 추론되지 않은 값이라, 그대로 두면 사용자에게 거짓 정보를 줍니다.

> 나중에 원본 라벨을 전수 집계해 보니 `chin_moisture`·`forehead_moisture`는 **원본에 100% 존재합니다**(턱 12,545건). 없는 값이 아니라 **학습 대상에 넣지 않은 값**이었습니다. 제거한 판단은 그대로 맞지만, 이건 **데이터가 받쳐 주는 지표를 서비스가 못 내보내고 있다**는 뜻이기도 합니다(§9). 같은 이유로 등급 `0`이 **"미검출"인지 "이상 없음"인지**를 `bbox_source`와 함께 구분했습니다.

### 7.3 "한쪽 눈이 측정되지 않는다" — 검출기는 정상이었다

서비스에서 한쪽 눈가가 측정되지 않는 현상이 보고됐습니다. 원인을 세 가지로 좁혀 **라벨 108,070건을 전수 집계**해 확인했는데 **셋 다 거짓**이었습니다.

| 가설 | 결과 |
|---|---|
| 좌/우 정의가 코드와 라벨에서 어긋난다 | **거짓** — 눈가·볼이 같은 규약(관찰자 기준) |
| 스마트폰 셀피 미러링으로 좌우가 뒤집힌다 | **거짓** — 세 기기 모두 같은 쪽 |
| 눈가 각도 필터가 볼과 같은 오류를 갖는다 | **해당 없음** — 눈가 필터가 아직 없었음 |

검출기도 정상이었습니다. YOLO 학습 산출물의 혼동행렬에서 **`l_eye` ↔ `r_eye` 오분류가 0건**이고 mAP50 0.994입니다.

**진짜 원인은 데이터셋 구조였습니다.** 정답 수가 이마·입술·턱 1,391건, 볼 1,388건인데 **눈가만 1,124 / 1,144로 18% 적습니다.** 비정면 사진에서 가려진 쪽 눈가에는 데이터셋이 애초에 라벨을 붙이지 않았고, 검출기는 그대로 학습해 그대로 동작하고 있었습니다.

그래서 문제는 검출이 아니라 그 다음입니다. 고개를 돌린 사진이 들어오면 한쪽 눈가가 미검출 → 전체 이미지 fallback → 얼굴 전체로 눈가 주름을 추론한 값이 다른 부위와 똑같은 모양으로 리포트에 실립니다. **조용히 틀린 값을 내보내는 것이 검출 실패보다 나쁩니다.**

### 7.4 등급 → severity 매핑 정본화

리포트의 `severity`는 `normal / mild / moderate / severe` **4개 어휘로 고정**돼 있고, 소비처가 `_SEVERITY_ORDER.get(severity, 0)` 패턴이라 **어휘 밖 값은 최저 등급으로 조용히 강등**됩니다. 여기에 세 가지 결함이 있었습니다.

| 증상 | 원인 |
|---|---|
| 등급 5가 `unknown`으로 누출 | 추론 엔진 매핑이 0~4만 정의 |
| 등급 4가 정렬에서 최하위로 취급 | `"very_severe"`가 어휘 밖 |
| 눈가 주름 등급 6의 결과가 **통째로 사라짐** | 파서 매핑이 0~5만 정의 → `None` → skip |

세 번째가 가장 나쁩니다 — **가장 심한 케이스가 리포트에서 없어집니다.** 정본은 파서의 라벨별 테이블이고, 이미 **라벨마다 상한이 다른 것을 정규화**해 두었습니다. 여기에 7등급 전용 테이블을 추가하고 추론 엔진을 정본에 맞췄습니다.

**어휘를 넓히지 않은 것이 핵심입니다.** `"extreme"`을 추가하는 편이 직관적으로 보였지만, 그러면 최고 등급이 정렬에서 최하위가 됩니다.

#### 같은 버그가 네 부위에 더 있었다

눈가를 고칠 때 **매핑 테이블 전체를 실측과 대조하지 않았습니다.** 뒤늦게 라벨 JSON 112,905건으로
전수 대조하니 네 라벨이 같은 상태였습니다 — 정의된 상한보다 실제 등급이 높고, 초과분은 `None`이 되어 skip됩니다.

| 라벨 | 매핑 상한 | 실제 상한 | 유실 | 유실률 |
|---|---:|---:|---:|---:|
| `glabellus_wrinkle` (미간) | 0~2 | **0~6** | 3,003건 | **23.94%** |
| `forehead_wrinkle` | 0~4 | **0~6** | 1,352건 | 10.78% |
| `forehead_pigmentation` | 0~3 | **0~5** | 143건 | 1.14% |
| `chin_sagging` | 0~5 | **0~6** | 13건 | 0.10% |

부위 레코드 137,995건 중 4,511건(3.27%) 이 매핑 밖이었습니다. **미간 주름은 네 번 중 한 번꼴로
리포트에서 항목 자체가 사라지고**, 이마 주름은 열 번 중 한 번입니다. 로그에 경고만 남고
사용자 화면에는 아무 표시가 없습니다.

새 테이블은 만들지 않았습니다 — 등급 수가 같으면 같은 정규화를 쓰면 되므로 눈가용 7등급 테이블과
기존 6등급 테이블을 **재사용**했습니다. 어휘도 4개 그대로입니다.

**고치면 기존 결과와 값이 달라집니다.** 척도가 길어지면 `severe`가 위로 올라가므로 중간 등급의
severity가 내려갑니다 — 미간 등급 2는 `severe` → `mild`가 되어 "최고 심각도"에서 "7단계 중 세 번째"가 됩니다.
**원래 척도가 그랬던 것이지 새로 정한 것이 아닙니다.**

이 버그는 라벨이 늘어날 때마다 재발하는 형태라, 값을 단언하는 대신 **`0..실측상한` 전 등급이 매핑에
덮여 있는지**를 검사하는 테스트를 붙였습니다. 실측 상한 테이블만 갱신하면 누락이 자동으로 걸립니다.
기존 테스트 한 건도 함께 고쳤습니다 — 이마 색소 등급 2를 `moderate`로 단언하고 있었는데,
그건 **틀린 상한(0~3)을 전제로 한 값**이었습니다.

### 7.5 추정값을 추정값이라고 표시하기

`bbox_source`는 **저장되고 있었지만 API 스키마에도 프론트엔드에도 없었습니다.** 저장만 하고 보여주지 않은 것입니다.

집계에 `mixed` 상태를 따로 두었습니다. 화면의 "눈가"는 좌·우를 묶는데 **측면 사진에서는 한쪽만 fallback**이 되므로, 이진값으로 뭉개면 "양쪽 다 추정"과 "한쪽만 추정"이 구분되지 않습니다. **값 자체는 숨기지 않았습니다** — 항목이 사라지면 사용자는 이유를 알 수 없습니다.

두 번째 방어선은 업로드 시점입니다. **추가 모델 없이** 검출 결과만으로 정면 여부를 판정할 수 있고, 이 데이터셋은 모든 이미지에 정답 각도가 붙어 있으므로 **임계값을 실측으로** 정했습니다(각도당 30장, 270장).

| 지표 | 정확도 | 오탐 | 미탐 |
|---|---:|---:|---:|
| 눈가 쌍이 모두 검출되는가 | 62.2% | 102 | 0 |
| **미간이 두 볼 중점에서 벗어난 정도** (임계 0.05) | **94.8%** | **0** | 14 |
| 같은 지표, 임계 0.06 | 95.6% | 5 | 7 |

첫 지표가 실패한 이유가 중요합니다 — **L15·R15에서는 두 눈가가 모두 검출됩니다.** 한쪽이 사라지는 것은 L30·R30부터입니다. 샘플 몇 장만 보고 일반화했다가 270장 실측에서 정정된 부분입니다.

임계값은 정확도가 더 높은 0.06 대신 **0.05를 택했습니다.** 오탐은 "측면 사진을 정면으로 통과시켜 추정값을 실측값처럼 내보내는" 실패이고, 미탐은 "재촬영을 한 번 더 권하는" 실패입니다. **정확도는 같은 단위로 세지만 비용은 대칭이 아닙니다.**

남은 약점도 기록해 둡니다 — 아래를 본 사진(angle 2)은 66.7% 입니다. 세로 항을 추가하면 나아질 것으로 보고 시도했지만 개선이 없어 되돌렸습니다. 세로 변위의 각도별 값이 angle 0 −0.067 / angle 1 +0.045 / angle 2 −0.020 으로, **아래를 본 사진이 정면보다 오히려 0에 가까웠습니다.**

## 8. 서비스 구성과 실행

**Backend (FastAPI)** — 인증·업로드·분석·추천·리포트 라우터와 4개 테이블 분해 파서, 목 AI 서버. `AI_INFERENCE_MODE`로 AI 서버 없이도 개발할 수 있게 분리했습니다.

**Frontend (Streamlit)** — 업로드, 부위별 리포트, 성분 추천 화면. 분석 결과 옆에 **데이터 상태와 검출 여부를 함께 배치**해, 사용자가 이 값이 실측인지 추정인지 같은 화면에서 확인할 수 있게 했습니다.

| 분류 | 기술 |
|---|---|
| AI · 학습 | Python 3.12, PyTorch, torchvision, timm(DINOv3), scikit-learn, Pandas |
| Backend | FastAPI, SQLAlchemy, Alembic, MySQL 8, Pydantic v2 |
| Frontend | Streamlit |
| 개발 환경 | uv, Docker, Git |

```bash
uv sync

# 크롭 → 특징 캐싱 → head 학습 실험
uv run python notebooks/jh/crop.py --faceparts 5 6      # 인자 없으면 볼
uv run python notebooks/jh/extract_features.py --split train --arch dinov3_s
uv run python notebooks/jh/train_head.py --target pore --grades 3
uv run python notebooks/jh/train_head.py --target pore --grades 3 \
    --reg-target cheek_pore --task both        # 분류 + 회귀

# README 실험 표를 로그에서 재생성
uv run python notebooks/jh/report_tables.py --check
```

> 학습에는 AI-Hub 원본 데이터(22.6GB)가, 서비스 실행에는 `.env`와 MySQL이 필요합니다. 둘 다 저장소에 포함되어 있지 않습니다.

| 수분 지표 미제공 | `chin_moisture`·`forehead_moisture`는 원본에 100% 있는데 학습 대상이 아니어서 서비스가 내보내지 못함(§7.2). 회귀 헤드(§6.8)로 낼 수 있는 값 |
| 회귀 단독 최적화 | 멀티태스크에서 회귀가 약간 손해를 봄(R² 0.509 → 0.482, §6.8). 회귀가 목적이면 헤드를 분리해야 함 |
| 수분 예측 | R² 0.268로 약함. 표면 텍스처와 연결이 약한 것으로 **보이나 확인하지 않음** |
| 백본 스케일업 | ViT-B/16은 CPU로 특징 추출에 2시간 이상 걸려 보류 |

## 10. 회고

**성능이 안 나올 때 어디를 먼저 봐야 하는가**를 배웠습니다. 처음에는 하이퍼파라미터와 증강을 만졌지만 실제로 성능을 끌어올린 것은 **라벨 정의를 바꾼 것**이었고, 그 전에 기준 지표를 accuracy에서 macro-F1으로 바꾸지 않았다면 개선인지 악화인지도 몰랐을 것입니다.

포크 이후 원본으로 다시 돌린 구간(§6.2~6.8)에서 배운 것은 조금 다릅니다.

**첫째, 제가 맞다고 믿은 전처리 규칙이 틀려 있었습니다.** 각도 코드를 반대로 읽어 가장 선명한 크롭을 버리고 있었고, 학습을 아무리 돌려도 지표로는 드러나지 않는 오류였습니다. **모델을 의심하기 전에 데이터를, 데이터를 의심하기 전에 내가 쓴 필터를** 먼저 봐야 한다는 걸 이때 배웠습니다.

**둘째, 실험이 빨라지면 새로운 종류의 오류가 생깁니다.** head 학습이 수 초로 끝나니 조건을 수십 개 비교할 수 있었는데, 그 편리함 때문에 각 수치가 시드 운을 얼마나 타는지를 한참 재지 않았습니다. **실험을 많이 돌리는 것과 믿을 수 있게 돌리는 것은 다른 문제였습니다.**

**셋째, 예측이 빗나가는 것이 실험의 실패는 아닙니다.** 눈가는 종횡비 왜곡 피해가 더 클 것이라고 두 번 적었는데 재보니 차이가 없었고, 등급 스케일 길이 가설은 프록시가 검증을 통과하지 못해 접었습니다. 이 경험 이후 **"~일 것으로 추정됩니다"와 "~로 확인됐습니다"를 구분해** 쓰기 시작했습니다.

**넷째, 라벨을 데이터로 검증할 수 있습니다.** §3에서 "라벨 경계가 모호하다"고 적었지만 그건 전제였습니다. 같은 JSON의 장비 측정값과 대조해 보고서야 어느 등급 경계에서 어떻게 무너지는지가 보였고, 등급 병합이 잘 들었던 이유도 다시 읽혔습니다 — 물리적으로 구분 가능한 단위로 묶여서가 아니라 클래스 균형 때문이었습니다. **문제 정의를 문장으로 쓰는 것과 숫자로 확인하는 것은 다른 일**이었습니다.

**다섯째, 같은 종류를 전수로 훑지 않으면 고친 게 아닙니다.** 눈가 주름 등급이 리포트에서 사라지는 것을 찾아 고치고 "정본화"라고 적었는데, 그때 **매핑 테이블 전체를 실측과 대조하지 않았습니다.** 뒤늦게 대조하니 같은 버그가 네 부위에 더 있었고 그중 하나는 제가 고친 것보다 심했습니다. 그래서 값을 단언하는 테스트 대신 범위를 덮고 있는지 검사하는 테스트를 붙였습니다.

아쉬운 점은 **제가 학습한 모델을 최종 서비스에 연결하지 못한 것**입니다. 운영 추론은 팀이 전환한 DINOv3 모델이 담당하고, 제 파이프라인은 실험 설정과 진단 기록으로 남았습니다.
